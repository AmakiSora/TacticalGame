# ark — 方舟算法

> 大逃杀模式（royale）独立设计的启发式内置算法：安全格容量匹配 + 逐行动点效益竞价 + 缩圈增援负担评估。
> 独立设计边界：只依据大逃杀规则、引擎行为与公开投影推导，不读取、不导入、不调用仓库内其他算法或策略辅助实现；现有算法仅作为黑盒对手运行，不参与设计。

## 设计原则

- **避难位置是共享资源**：同时回合下多个单位若各自贪心奔向“当前最好的格子”，会挤在同一个安全点并在结算时互相占位。方舟先把所有可移动友军与可落脚格建成二分图，用最小费用匹配一次性分配互不相同的目标格。
- **按行动点而不是按单位决策**：每个行动点只选一个动作或一个两动作组合，按“收益 ÷ 行动点^0.85”竞价；入队后重新投影队列再算下一次，避免一次规划整轮。
- **只读公开状态与自己的队列**：使用公开投影中的地形、单位、据点、资源、炮火与配置；不读取 `rngState`、token、对手隐藏队列或其他席位计划，也不修改传入快照。
- **不依赖传入策略工具**：`utils` 参数不使用；形状覆盖、寻路、伤害分布、匹配与估值全部在文件内独立实现。
- **参数全部取自本局配置**：兵种数值、形状/射程/锁定、`attacksPerUnit`、行动点、炮火伤害/间隔/最小半径、据点收入/折扣/可部署标记均实时读取；不按地图名、对手名或实体 id 分支。
- **确定性**：不使用随机数；同一公开状态与队列给出同一动作。

## 算法原理

### 1. 公开状态镜像与队列前缀投影

`context()` 复制公开棋盘与存活单位，并叠加 `terrainCells` 的地形覆盖；随后按己方队列顺序投影：

- `move`：更新单位坐标并累计移动次数；
- `demolish`：把目标格地形改为 `plain`；
- `deploy`：扣除折后补给，生成带 `planned` 标记的新单位（本轮不可再行动）；
- `attack`：累计攻击次数，按期望伤害削减目标 HP；
- `heal`：若支援者自身或覆盖区域内任一图内格处于炮火危险区，则整次治疗不生效；否则按 `healPower + healVarianceRange / 2` 治疗覆盖到的友军。

投影后的占位集合包含所有友军与敌军。攻击预留期望伤害但**不提前释放敌军占位**，避免“预计击杀”后抢一个结算时仍被占用的格子。

### 2. 闭式伤害分布

`damageStats()` 把伤害视为 `attack - defense ± damageVarianceRange` 上的离散均匀分布，按引擎的下限与 HP 截断计算期望伤害和击杀概率。实现为常数时间闭式求和，不逐点枚举：

- 方差为整数或非整数时，余数按尾部权重折算；
- 方差超过浮点精确整数范围时，改用连续均匀分布极限；
- 配置中所有兵种 `attack = 0` 时仍使用 `minimumDamage`，归一化分母至少为 1。

### 3. 来敌威胁

`incoming()` 对每个敌军估计其对某格的威胁：

- 当前即可覆盖该格：`attackLock` 兵种权重 0.95，否则 0.72；
- 仅在“射程 + 移动力”内可达：权重 0.2；
- 按剩余 HP 与单发威力缩放，再按席位取威胁最高的 `actionsPerTurn` 个求和，近似“一轮内最多能吃到的集火”。

它不是敌方计划预测，也不模拟攻击目标选择。

### 4. 安全格容量匹配

`shelters()` 为所有未排部署的友军分配目标格：

- 候选格为地图内的 `plain` 格，排除敌军占位与已排部署友军占位；允许当前友军之间互换位置，但不保证结算顺序；
- 每个单位另有私有 dummy 泊位，保证满图时匹配仍可行；单位匹配到别人的 dummy 或不可达格会被极高费用拒绝；
- 费用由地形行军距离、最终最小安全半径外的暴露、接敌风险、可射击位置奖励与未来炮火成本组成；
- 用 Hungarian 最小费用匹配求全局分配，而不是逐单位贪心。

费用参数：

```text
0.65 × travel / moveRange
+ 1.1 × max(0, radius - minimumSafeRadius)
+ 0.65 × min(4, incoming / hp)
- 0.6 × (该格可射到任一敌军)
+ 2 × stormCost / unitValue
```

### 5. 格子与行动估值

`positionValue()` 评价某单位位于某格的价值：到其分配避难格的剩余路程、当前接敌风险、炮火成本、可射击敌军的价值、与最近敌军的距离，以及可占领据点的收入窗口。据点窗口按 `roundsSafe()` 与实际 `nextShrinkRound` / `intervalRounds` 推算，最多计 4 轮；`canDeploy: false` 的据点不产生部署估值。

`attackValue()` 估计一次瞄准的收益：期望伤害占目标最大 HP 的比例、击杀奖励（该席位最后一个单位提高到 1.6 倍），并乘以可靠性。可靠性考虑敌军下一拍能否离开瞄准覆盖：

- `attackLock` 兵种：目标无可移动落点时 1，否则 0.92；
- 非锁定兵种：有逃生格时按是否处于下一轮炮火区给 0.5 / 0.84，并随队列位置每拍衰减 0.025，下限 0.3；无逃生格时为 1。

`healingValue()` 只统计实际缺失 HP；若目标即将承伤超过其半血，治疗权重提高到 2 倍。支援者或覆盖区域的任一图内格处于炮火危险区时，治疗价值直接为 0。

`demolishValue()` 只对重装生成：评估为附近友军打通更靠内安全区的捷径收益；若未来安全区容量不足，再追加拥堵缓解价值。

### 6. 单动作与两动作竞价

`choose()` 枚举：

- 单动作：攻击、治疗、爆破、移动、部署；
- 两动作组合：攻击 → 移动、移动 → 攻击、移动 → 治疗、移动 → 爆破。

移动候选按目的地收益排序，组合只使用收益最高的落点；后续攻击/治疗/爆破按投影后的新位置重新生成瞄准。每个候选得分 `value / actions^0.85`，只有严格超过 0.001 才成为当前最优；返回组合的第一个动作。剩余行动点不足时不会生成超长组合。

攻击次数按队列中该单位已排攻击数与 `attacksPerUnit` 限制；治疗只由 `support` 生成；爆破只由 `heavy` 生成；已部署的新单位带 `planned` 标记，本轮不再参与。

### 7. 缩圈增援

部署只考虑己方且 `canDeploy !== false` 的据点，落点必须是相邻、未被占用、非危险区的 `plain` 格；费用按据点折扣计算并封顶到 0。零兵力时使用生存优先分支：只要首步能部署就优先部署，避免步骤末立即淘汰。

常规增援按以下因素竞价：

- `readiness`：单位价值 × 机动准备（`sqrt(moveRange)`，射程每多 1 格加 35%）× 支援重复度 × 疏散机动性；
- `efficiency`：`sqrt(value / cost)`；
- `capacity`：军队越大，边际增援收益越低；
- `risk`：落点来敌威胁 / 单位 HP；
- `stormCost`：下一拍及未来三拍炮火风险；
- `burden`：全军当前位于未来安全区外的疏散负担。

```text
gain = readiness × 0.55 × efficiency × capacity
     - value × risk × 0.65
     - stormCost
     - burden × value × 0.035
```

### 8. 决策入口

`decide()` 在以下任一条件成立时返回 `null`：模式不是 `royale`、对局未处于 `active`、没有显式 `ctx.owner`、该席位已淘汰、计划不存在或已提交、队列长度达到 `actionsPerTurn`。否则构建上下文并返回一个动作；`null` 表示本席位不再追加动作，由调用方提交或等待结算。

### 必须守住的约束

- **不读对手信息**：只读自己的队列（`plan.myQueue` 或 `plan.queues[owner]`），不读其他席位计划、token、`rngState`；
- **不修改输入**：所有投影都在副本上进行；
- **部署合法性**：只从己方据点、`canDeploy !== false`、相邻平地、非危险、非占位；折扣后费用不超过补给；
- **零兵力优先部署**：队列第 1 步就必须部署，否则步骤末可能立即淘汰；
- **攻次与队列投影**：同一单位一轮攻击次数受 `attacksPerUnit` 限制，攻击必须基于投影后的位置与地形；
- **治疗危险区**：支援者或覆盖区域任一格处于炮火区时，不得把治疗当作有效结算；
- **爆破只对重装**：且不能重复爆破已由自己队列清空的格子；
- **形状合法性**：line 的瞄准格必须是该方向首个地图内格，arc 只在距离 1 生效，single 攻击不能瞄准自身格。

## 性能表现

### 固定实现黑盒评估

引擎 **3.8.19**，日期 **2026-10-29**，harness 为未修改的 `scripts/horizon-arena.mts`；方舟与三个对手均为 **v1**。只统计最终固定实现的 **71 局**，开发调参批次与 HTTP 接入局不计入。数字为方舟视角的 **胜 / 负 / 平**。

| 对手 | 狭路 2 人 | 雪花 2 人 | 雪花 3 人 | 雪花 6 人 | 合计 |
|---|---|---|---|---|---|
| `random-royale` | 8 / 0 / 0 | 8 / 0 / 0 | 3 / 0 / 0 | 6 / 0 / 0（6 局） | **25 / 0 / 0** |
| `echelon` | 8 / 0 / 0 | 8 / 0 / 0 | 3 / 0 / 0 | 6 / 0 / 0（6 局） | **25 / 0 / 0** |
| `apex` | 4 / 0 / 4 | 2 / 6 / 0 | 0 / 3 / 0 | 1 / 0 / 1（2 局） | **7 / 9 / 5** |

- 总计 **57 胜 / 9 负 / 5 平**；66 局 `last_player_standing`、5 局 `mutual_annihilation`；双方非法入队 **0**，`round_guard` 截断 **0**。
- 结算期仍有动态失败：占位 130 次、前序失败连锁 117 次、单位已消失 78 次、到达冲突 37 次。这些是隐藏计划统一结算后的合法失败，不代表方舟已经能规避碰撞。
- 双人种子基 `291903`，多人 `391903`；实际种子为基数加 `floor(index / 2) * 7919`。双人成对换座；方舟在多人局只坐一个席位，其余席位均为同一对手算法。
- 狭路对 `apex` 的四组 A 席结果完全重复（胜局与同归于尽局各半），不是四份独立证据；雪花双人 2:6、三人 0:3 表明对强对手仍有明显短板。
- 计时与其他评估、全量测试并发：方舟最大单次决策 **110.6 ms**，最大单轮决策累计 **425.7 ms**，仅为本批次观测，不作严格性能基准。
- 原始 JSONL 只落本地 gitignored `temp/ark-arena/final-*.jsonl`（12 个文件），未写入 `arena/matches.jsonl` 或正式排行榜。

### 决策时间

同一 harness 下，方舟的决策通常远快于同场对手：狭路双人最大单次决策 2.8 ms；雪花双人最大 62.2 ms；雪花六人最大 110.6 ms（并发负载下）。单次决策复杂度主要来自每步重新做的 Hungarian 匹配（O(单位³)）、每格威胁估计与两动作组合枚举。

## 已知限制

1. **不是同时结算搜索**：只投影己方队列；敌军的移动、攻击与治疗全部未知，避难匹配不能保证避开隐藏计划的到达冲突，结算期占位/冲突失败仍有 130/37 次。
2. **威胁模型是启发式**：`incoming()` 不模拟敌方目标选择、攻击锁定与集火顺序，只按席位取最高威胁求和；可靠性衰减是对逃生格的粗估，不是完整概率分布。
3. **对强对手仍落后**：雪花双人对 `apex` 2:6、三人 0:3；狭路对 `apex` 的四组是确定性重复轨迹，不能当作 4 场独立胜利。方舟不承诺战胜现有或未来全部对手。
4. **组合深度只有 2 个行动点**：只枚举单动作与两动作组合，且移动组合只使用当前收益最高的落点；没有三动作链、部署后行动或多单位联合行动。
5. **匹配与移动未做结算顺序协同**：允许友军互换目标格，但没有为同格轮换安排队列顺序，仍可能在结算时冲突。
6. **没有末轮专门搜索**：大逃杀以存活为目标，方舟没有针对最后几轮/最后单位的有限回合裁决搜索；末轮行为仍由同一套启发式估值决定。
7. **部署权重手工标定**：readiness、capacity、burden 的系数未做在线拟合；不同经济或兵种配置下可能偏离最优。
8. **评估覆盖有限**：只测两张现有大逃杀图、三个对手、2/3/6 人，且六人对 `apex` 只有 2 局；没有未见地图、混合对手阵容、8 人局或独立留出集。
9. **治疗与伤害用期望值**：治疗按均值加半方差估算，攻击按期望伤害与击杀概率估值，不显式处理方差风险或溢出。

## 优化方向

1. **碰撞感知规划**：在己方队列投影之外，加入对敌军可达集的粗略占位预报，降低结算期 `destination_occupied` / `destination_conflict`。
2. **更强的威胁模型**：按敌军射程、锁定、行动点与目标价值估计集火分布，而不是简单的最高威胁求和。
3. **三动作与部署后行动**：把“部署 → 移动/攻击”纳入组合竞价，减少新兵原地待机。
4. **末轮与残局专门化**：在最后几轮按存活、击杀与炮火时间线做有限深度搜索。
5. **独立留出评估**：增加未见地图、混合对手、8 人局与固定留出种子，避免在同一批种子上调参。
6. **参数标定**：在不改变设计结构的前提下，用独立种子对匹配费用、行动竞价指数与增援系数做离线校准。

## 兼容性

- **模式隔离**：仅注册 `royale`；其他模式的大厅、runner 与评估链路会直接拒绝，`decide` 也返回 `null`。
- **地图无关**：不读地图文件名或 id；`cells`、`terrainCells`、据点、炮火配置与兵种表全部来自公开状态。
- **配置无关**：不同的 `actionsPerTurn`、`attacksPerUnit`、形状/射程、伤害/治疗方差、炮火间隔/伤害/最小半径、据点收入/折扣/`canDeploy` 都能直接生效。
- **无外部依赖**：ESM 单文件，零 import，无文件/网络/环境变量访问；可在 Node 24 下直接加载。
- **接口**：实现 `decide(view, utils, context)`，返回 `{type, payload}` 或 `null`；同步纯计算，不实现 `playTurn`。

## 使用方式

### 通过前端添加

大厅选择大逃杀模式地图 → 添加机器人 → 「算法脚本」标签 → 选择「方舟算法」。评估控制台中仅在大逃杀模式目录出现。

### 通过命令行运行

```bash
node algorithms/runner.mjs --algorithm ark --url http://localhost:3100 \
  --game <gameId> --token <playerToken> --side player_a
```

### 通过 API 添加

```bash
curl -X POST http://localhost:3100/api/games/<gameId>/bots/algorithm \
  -H "X-Host-Token: <hostToken>" \
  -H "Content-Type: application/json" \
  -d '{"botType":"algo_ark"}'
```

```bash
out="temp/ark-recheck-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$out"
```
