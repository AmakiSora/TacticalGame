# bastion — 堡垒算法

> 大逃杀模式（royale）独立设计的启发式内置算法：逐行动点束搜索 + 存活/进攻双向位置
> 价值 + 敌方威胁场 + 接敌梯度 + 集火斩杀 + 缩圈炮火约束 + 逐步合法性重放。
> 独立设计边界：只依据大逃杀规则、公开投影与共享规则推导，不读取、不导入、不调用
> 仓库内其他算法或策略辅助实现；现有算法仅作为黑盒对手运行，不参与设计。

## 设计原则

- **逐行动点束搜索**：每步基于公开快照与己方已排队列重新规划，对「剩余行动点内可以
  打出什么动作序列」做束搜索（beam width 10、软时间预算 85ms），而不是只看单步最优。
  这样可以发现「移动 → 攻击」「多单位接力集火」这类两步以上的组合。
- **存活与进攻并重**：位置评估既算「被威胁」的暴露惩罚，也算「我威胁到敌人」的进攻
  覆盖奖励，并加到最近敌人的接敌梯度——只罚不奖会让单位永远停在敌方射程外沿、全程
  零攻击；接敌梯度按地图尺寸自适应（开阔大图全力追击、紧凑小图收敛防深入）。
- **集火斩杀为胜负手**：攻击收益对残血目标额外加权，鼓励集中火力收人头（收割者银行
  全额成本），而非把伤害平摊给满血单位。
- **只读公开状态与自己的队列**：使用公开投影中的地形、单位、据点、资源、炮火与配置；
  不读取 `rngState`、token、对手隐藏队列，也不修改传入快照。
- **参数全部取自本局配置**：兵种数值、形状/射程/锁定、`attacksPerUnit`、行动点、
  炮火伤害/间隔/最小半径、据点收入/折扣/可部署标记均实时读取；不按地图名、对手名或
  实体 id 分支（接敌驱动力只依赖地图半径这一公开几何量）。
- **合法性在坐标空间判定 + 逐步重放**：候选生成与校验与引擎 `planning.ts` 同口径；
  终局再做一次按行动步的合法性重放（`sanitizeActions`），剔除落点占用、部署冲突与
  「攻击已被己方前序攻击打死目标」的浪费动作，杜绝无效行动点。

## 算法原理

### 1. 敌方威胁场

`computeThreat` 对每个敌军按「移动 + 射程」的真实可达范围展开，把它的原始火力
（`attack × 锁定权重`）累加到它下一拍能打到的每个格子。这是一张位置无关的威胁场
（本方规划期内敌军位置不变），评估时按受击方实际防御折算期望伤害并做集火上限。

### 2. 位置评估

`unitValueAt` 评估某单位位于某格的价值：

- 存活价值：`cost × (0.4 + 0.6 × hp/maxHp)`，残血单位价值下降；
- 缩圈风险：本轮安全半径外重罚，下一拍安全半径外轻罚；
- 威胁暴露：按实际防御折算期望伤害、上限到当前 HP，再乘阶段威胁权重（建造期低、
  缩圈后期高）与存活比例；致死暴露额外平方级重罚；
- **进攻覆盖奖励**：本格能打到的敌军战力折算为正向价值，确保「敢推进到攻击位」压过
  威胁规避的保守倾向，并叠加一个攻击位硬奖励；
- **接敌梯度**：靠近最近敌人给单调奖励，让近战在抵达攻击位前就有持续向前的动力；
  梯度强度按地图半径自适应（`approachDrive`）；
- **抱团协同**：靠近友军小幅加分、孤立无援轻罚，避免单兵突进被逐个点掉；
- 占点前景：`canCapture` 单位对本方未持有据点的接近/占领奖励。

### 3. 动作候选与束搜索

`expand` 对每个己方单位枚举：攻击（含形状覆盖、锁定按初始敌位、还击惩罚、残血目标
集火加权）、移动（可达集内每个格子，投影占位拦截、逼近激励）、治疗（支援）、爆破
（重装），以及全局的部署。束搜索逐行动点扩展、每层保留 `BEAM_WIDTH = 10` 条最优，
终局用「累计收益 + 收官位置价值」择优，再经 `sanitizeActions` 逐步重放剔除非法动作。

### 4. 部署经济

`deployExpand` 的净值 = 本征价值 × **性价比因子（`eff³`，强烈偏向每点费用战力更高的
远程兵种，避免全爆昂贵近战重装被远程风筝）** × 威胁折损 × 军队容量
（`1/(1+0.12×army)`）。零兵力时生存优先（净值放大）；兵力领先 3 个即停止扩张。

### 5. 逐步合法性重放

引擎按行动点（步）结算、每步先离场后进场，且某单位某步硬失败后其后续动作作废。束搜索
按「整轮终局」判占位会误判，`sanitizeActions` 按步重放：跟踪己方/敌军占位与敌军 HP，
剔除落点被占的移动、占位冲突的部署、以及攻击已死目标的空刀，保证排出的队列行动点
几乎不被 `destination_occupied` / `unit_gone` 浪费。

## 决策时间

harness 观测（snowflake / narrow-road 双人，8 局/对手，全部对手）：单次决策最大
**约 40 ms**、均值约 17 ms，远低于 100ms 上限（对比 apex 同场景峰值 600ms+）；束搜索有
`TIME_BUDGET_MS = 85` 软时间预算兜底，超时即停止扩展、用已有最优序列。

## 已知限制

1. **对 apex / ark 的特定组合仍落后**：snowflake 对 ark、narrow-road 对 apex 仍处下风；
   这些是历经多版标定的强算法，堡垒不承诺战胜现有或未来全部对手。
2. **威胁场是启发式**：只按移动+射程近似敌方下一拍可达范围，不模拟敌方目标选择与
   集火顺序。
3. **束宽有限**：`BEAM_WIDTH = 10`、无对手响应建模，不是完整的对抗搜索。
4. **部署/接敌权重手工标定**：容量衰减、性价比指数、接敌梯度系数未做在线拟合。

## 兼容性

- **模式隔离**：仅注册 `royale`；其他模式的大厅、runner 与评估链路会直接拒绝，
  `decide` 也返回 null。
- **地图无关**：不读地图文件名或 id；`cells`、`terrainCells`、据点、炮火配置与兵种表
  全部来自公开状态。
- **配置无关**：不同的 `actionsPerTurn`、`attacksPerUnit`、形状/射程、伤害/治疗方差、
  炮火间隔/伤害/最小半径、据点收入/折扣/`canDeploy` 都能直接生效。
- **无外部依赖**：ESM 单文件，零 import，无文件/网络/环境变量访问；可在 Node 24 下
  直接加载。
- **接口**：实现 `async decide(view, utils, context)`，返回 `{type, payload}` 或 `null`；
  不实现 `playTurn`。

## 使用方式

### 通过前端添加

大厅选择大逃杀模式地图 → 添加机器人 → 「算法脚本」标签 → 选择「堡垒算法」。

### 通过命令行运行

```bash
node algorithms/runner.mjs --algorithm bastion --url http://localhost:3100 \
  --game <gameId> --token <playerToken> --side player_a
```

### 本地黑盒评估

```bash
out="temp/bastion-arena/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$out"
for opponent in random-royale echelon apex ark; do
  for map in narrow-road snowflake; do
    node --import tsx scripts/horizon-arena.mts --a bastion --b "$opponent" \
      --map "$map" --players 2 --games 8 --seed-base 291903 \
      --out "$out/$map-2-$opponent.jsonl"
  done
done
```

harness 对 `--out` 追加写入，复跑请使用新目录。报告只写入 `temp/`，不修改
`arena/matches.jsonl` 或正式排行榜。

## 一句话总结

堡垒用逐行动点束搜索规划整轮，以「存活 + 进攻覆盖 + 接敌梯度 + 集火斩杀」的双向位置
价值与缩圈炮火约束走位，经逐步合法性重放保证行动点效率；对随机/雁阵稳定取胜、对绝境
与方舟在部分地图互有胜负，但在个别地图组合对顶级算法仍处下风。
