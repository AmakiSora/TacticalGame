## 定位

同时回合的每一轮，都是一次"盲下整份有序计划、按行动点分步同时结算"的博弈。现有四个同时算法都只看**一轮**：

- dest-prob 给单个动作估期望收益，逐个边际贪心；
- kriegspiel 把整份计划放进分步结算器 rollout 一轮，用裁定权重给结算后棋盘收口；
- matrix-eq 把一轮升维成计划组合的矩阵博弈，求均衡混合。

单轮视野在这两张图上都有已知代价：kriegspiel v2 在 molten-throne 被 matrix-eq 斩首 2:28（kriegspiel 档案「已知短板」）；本次开发前的基线实测里，matrix-eq 在 molten-throne 对 dest-prob 8:0 全是斩首（8 局，harness 同下，开发期种子）——一轮之内"再挨一下换一格据点"总是划算的，三轮之后总部就没了。

视界算法的核心问题换成了：**这一整份有序计划真打一遍之后，棋盘投影到终局，我赢的概率是多少？** 结算这一步和 kriegspiel 一样必须逐条镜像引擎（这是题目要求），区别全部在"结算后怎么定价"和"对手怎么来"。

### 与其它算法的路线差异

| 维度 | dest-prob | kriegspiel | matrix-eq | **horizon** |
|---|---|---|---|---|
| 评估对象 | 单个动作的解析期望 | 一轮结算后的棋盘，按裁定权重直接加总 | 计划组合 × 场景的支付矩阵 | 一轮结算后的棋盘**投影到终局**：据点到达时间模型、两轮攻城压力、下一轮威胁场 |
| 评估输出 | 期望分 | 分数均值 − λ·标准差 | 均衡下的期望支付 | **胜率**（投影终局分差 → logistic，σ 随剩余回合 √R 收窄）× 歼灭风险；领先自动保守、落后自动冒险 |
| 多轮信息 | 无 | 无（单轮 rollout） | 无（单轮矩阵）+ 事件史校正 | 有：据点剩余回合期望持有、未来两轮总部承伤、下一轮存活率 |
| 对手模型 | 固定启发式落点分布 | 三种性格随机采样 | 镜像生成器 + 事件史重建 + CFR 均衡 | **同构规划器**（对手座位上跑同一个束搜索，对手眼中他人静态开火）+ 静态开火 + 扰动贪心 + 斩首变体 |
| 防"被一戳就破" | 无 | 风险项 λ·std | 均衡不可利用性 | **对抗探针**：对首选计划求对手最优回应，并入场景后重排决赛圈 |
| 搜索 | 边际贪心 | 种子计划 + 爬山 | CFR 迭代 | 逐行动点束搜索（宽 3，决赛圈 8） |
| 是否读事件史 | 否 | 否 | 是（`round_resolved`） | **否**：只读当前棋盘与 `plan.myQueue` |
| 输出确定性 | 确定 | 确定 | 混合抽样 | 确定（墙钟只作安全网，正常局面不触发） |

一句话：**kriegspiel 问"这份计划打完一轮值多少分"，horizon 问"这份计划打完一轮之后，这盘棋我还能赢几成"。**

## 通用性约束

- **不读地图身份**：源码里没有 `mapId` / `map.name` / 任何地图名，也没有坐标常量（单元测试 `horizon 通用性自查` 对源码做正则断言；交付自查 `grep -niE "standoff|molten|mapId|map\.name"` 无输出）。
- **地图差异只从公开状态进入**：兵种数值与攻击/治疗形状、`attackLock`、`healRange` 来自 `game.config.units`；行动点、`attacksPerUnit`、伤害/治疗方差、`deployFromHq`、据点类型（收入/折扣/`canDeploy`）、裁决权重（含 `controlPointFlowRatio`、`killValue`）、`maxTurns`（`null` 时用 8 轮开放视界）来自 `game.config.balance`；格子、地形与覆盖层来自 `game.cells` / `game.map.terrainCells`；据点与归属来自 `game.controlPoints`；炮火危险格（若有）来自 `game.artillery`。
- **胜率尺度也从配置推导**：单轮摆动 = 1.2 × max(1.5 × 据点权重, 总部伤害权重 × 平均单兵对总部伤害)，不按图调参。
- **多席位**：座位按 `turn.turnOrder` 的存活顺序建模；评估把对手分做 log-sum-exp 软最大（要压过"最强那家"）；对手建模只对最近的两家跑同构规划，其余静态开火；3 / 6 人局都有合法性回归与胜率抽样（见「验证」）。
- **无隐藏信息**：只用 API 快照与己方 `plan.myQueue`；不读 `round_resolved` 事件史，也不推测服务器未下发的对手计划。
- **无算法依赖**：不 import / 调用任何其他算法；分步结算镜像以 `simultaneousResolve.ts` 为唯一参考（交付自查 `grep -n "builtin/"` 无输出）。

## 决策流程

### 0. 前置短路

`ctx.owner` 缺失、`phase !== 'active'`、模式不是 `simultaneous`、己方非存活、已在 `plan.committed`、或 `plan.myQueue.length >= actionsPerTurn` 时返回 `null`。座位只从 `ctx.owner` 取（同时模式没有 `currentPlayerId`）。

### 1. 每轮规划一次，缓存与对账

以 `${gameId}|${owner}|${roundNumber}` 为键缓存整份有序计划。之后每次 `decide` 先把 `plan.myQueue` 解析成内部动作，与缓存计划的前缀逐条对账（顺序敏感，两个连续 `wait` 不会被去重吞掉）；一致就吐出下一条，不一致就以现有队列为固定前缀重新规划。吐出前再过一遍合法性镜像。

**被拒处理**：若上次吐出动作后队列长度没变（说明没入队），把它记入禁用表并重新规划，绝不重复同一动作——runner 的"被拒后继续 decide"语义下不会空转到 20 次上限。

### 2. 本轮模型

格子下标化、邻接表、地形（覆盖层优先，与 `gameIndex.buildIndex` 同序）、**全源地形 BFS 距离**（只按水/障碍寻路，单位与总部不挡路，与 `planning.ts` 计划期寻路同口径）。单位按 `game.units` 数组顺序建模（引擎的占位与结算先后依赖这个顺序）。兵种、格子、座位全部整数下标化，威胁区/攻城位/覆盖格都按整数下标缓存。

### 3. 计划期合法性镜像（对齐 `planning.ts`）

`projectPrefix` 给出前缀执行后的虚拟站位、每单位攻击计数、部署花费与预留落点、自有爆破清出的地形。`isLegalNext` 逐条对齐 `checkMove` / `checkAttack` / `checkHeal` / `checkDeploy` / `checkDemolish`：移动按投影地形 BFS ≤ moveRange 且不是原地；攻击按投影站位重算形状（`single` / `line` / `arc`，射程截断、`attacksPerUnit`）；治疗按 `healShape` 与 `healRange ?? attackRange`；部署按起点（`deployFromHq`、据点归属与 `canDeploy`）、相邻、投影平地、补给扣除前缀花费；爆破要重装、相邻、投影为障碍。占用与冲突按引擎口径**不在计划期判**。

### 4. 分步结算镜像（对齐 `simultaneousResolve.ts`）

每步：级联预检（单位已亡 → 记失败单位；先前硬失败 → 作废）→ 步初占位快照（单位优先、数组顺序第一个，再总部）→ 到达判定（同格多到达全失败、阻挡/总部/未移出单位占用失败、依赖链迭代传播，允许交换与链式腾格）→ 部署（按座位顺序扣补给、据点折扣按当前归属）→ 移动 → 爆破（下一步起生效）→ 攻击/治疗（按结算站位重算覆盖；`attackLock` 锁定**计划时刻**点击格上的非己方单位、逃出射程才落空；超 `attacksPerUnit` 或瞄准失效记失败并级联；先治疗后扣伤；击杀与总部伤害按最后一击入账）→ 死亡与淘汰（单位移除、据点中立）→ 终局检查；不终局才在轮末按 `turnOrder` 占点。伤害与治疗用**期望值**（期望伤害按 `max(minimumDamage, atk − def + U{−v..v})` 精确求期望），因此搜索可复现。

### 5. 视界评估（结算后棋盘 → 终局投影 → 胜率）

`projectScores` 用 `engine.scorePlayer` 的同一公式投影各座位的**终局**裁决分：

1. **下一轮威胁场**：每个存活单位在原地可打格计 1、走一次后可打格计 0.65，累加到"座位 × 兵种 × 格"的期望伤害场；单位存活率 = 1 / (1 + (k/0.8)³)，k = 威胁 × 0.45 / 当前血量；军力按存活率折算。
2. **据点到达时间模型**：各方最近占点单位到该据点的到达轮数（受威胁单位按存活率推迟）；格上站着某方单位时，其余各方要先拔点（再推迟 1.5 轮）。持有方保有到**最早的对手到达**为止，其后按 exp(−到达轮数/1.5) 分摊剩余回合，持有方单位已守在点上 ×1.5；中立据点没人来就保持中立。据点收入按投影持有回合计入经济项（补给按军力权重 0.8 折算——补给本身不计分，但会变成部队）。
3. **两轮攻城压力**：每个攻城位只容一名攻击者（贪心匹配），守方单位站住的攻城位不可用（近战贴身封堵），攻击者在攻城位上的价值按守方威胁场折算存活率；每轮按行动点预算贪心排兵（在位的先开火，余下行动点给最近的攻击者走位、到位还有点数就补一枪），首轮 ×0.85、次轮 ×0.5。投影分按剩余血量封顶，**歼灭风险用未封顶的压力**：risk = logistic(4 × (压力/血量 − 1))。
4. **胜率**：双人局 value = (1 − 我方风险) × (对方风险 + (1 − 对方风险) × Φ)，Φ = logistic(1.7 × 投影分差 / σ)，σ = 单轮摆动 × √(剩余回合 + 1)；多人局对手分取软最大，只乘我方风险。再加一个很小的线性分差项保证胜率饱和时仍有梯度。本轮就被歼灭的局面返回 −0.5 + 0.1 × (被歼行动点 / (A+1))——多撑一步也有区别。

### 6. 场景集（对手模型）

每名需要建模的对手四套计划：**同构贪心**（同一束搜索、宽 1，对手眼中其他人静态开火，权重 0.40）、**静态开火**（原地对当前站位挑最好瞄准，0.20）、**扰动贪心**（每步在候选里按扰动分挑，0.25）、**斩首变体**（同构规划 + 本轮总部伤害额外加价，0.15）。双人局建模唯一对手，多人局只建模最近两家。场景集还在己方空计划下预演一遍，得到对手单位**逐行动点**的落点分布，作为己方瞄准的先验。

### 7. 候选生成与束搜索

逐行动点在前缀投影局面上枚举：每单位攻击前 3（按落点分布 × 期望伤害，敌方总部恒中 ×3、锁定射击按锁定命中）、治疗前 2、移动前 5（按"只动这一个单位"的静态视界分预筛，排除注定失败的格：敌方当前站位、总部、己方投影站位与预留部署格）、重装相邻爆破、部署前 4（每兵种至多 2 格）、`wait`。束宽 3、最后一层保留 8 个决赛圈；每个前缀在全部场景下真实结算并取加权平均胜率。

### 8. 对抗探针与输出

对首选计划，让每个相关对手用同构规划求**最优回应**（己方计划已知），把它作为权重 0.3 的新场景并入，对决赛圈重排取最优。去掉末尾 `wait` 后缓存并逐条吐出。墙钟预算 900ms 只作安全网（对手建模 ≤30%、束搜索 ≤85%；被截断时用主场景贪心补满剩余行动点，硬上限 1.1×）；正常局面远用不满（见「决策耗时」）。

## 已知限制

1. **molten-throne 的据点流量弱于对手**：对 dest-prob / kriegspiel 每轮平均持有 7.1–7.4 格，对手 11.9–12.5 格；能赢是因为第 11 轮前后就把对方总部（100 血 / 防御 3）打掉了。如果遇到总部防守远强于现有四个算法的对手，这条路线可能变成"总部没打下、据点又落后"的裁决败局。到达时间模型给每个据点只看"最近的一个占点单位"，24 格密集据点上一名侦察兵同时"支撑"多格，系统性高估了自己扩张的速度（推断，未做对照实验）。
2. **matrix-eq 在 molten-throne 仍能斩首 3/30**：三局都是 horizon 一点总部伤害都没打出（第 7 / 14 / 15 轮被歼）。对手模型的四套场景都是"本轮最优"的近似，matrix-eq 的混合策略会在几轮里分批把侦察兵堆到总部邻格；两轮攻城压力窗口对"慢慢聚兵"的预警偏晚。
3. **standoff 对 matrix-eq 1 负是 588 : 588（四舍五入后相同）的裁决分惜败**，双方都没打到总部；说明裁决局里的据点流量仍是 horizon 的相对短板（对 kriegspiel 2.76 vs 3.87）。
4. **评估是启发式投影**：存活率、到达时间、攻城压力的系数（0.45、0.65、1.5、0.85/0.5 等）在开发期按两张图的对局调过；它们只经配置换算尺度，没有在第三张同时回合图上验证过。新图上的强度是**未标定**。
5. **多席位只做了抽样，且 6 人局结论不稳**：3 / 6 人局每格 6–12 局、对手全部同型；3 人局对 kriegspiel 只有 5:4；6 人局对 matrix-eq 两次复测 1:5 与 9:3 互相矛盾（见上表注）。混合对手的多人局只跑过合法性（HTTP 6 人 3 轮）。
6. **耗时随单位数增长**：6 人局与 molten-throne 中后期单轮规划可到 0.5–0.9s（见「决策耗时」）；在 CPU 争用严重的机器上墙钟安全网会提前截断搜索，强度随之下降，且不同负载下的同一快照可能给出不同计划。
7. **不覆盖 royale / annihilation**：炮火缩圈、无总部与兵力打光淘汰都不在镜像与评估里；`decide` 在这些模式下直接返回 `null`（只注册 simultaneous）。
8. **本地多 bot 验证要调高服务器限流**：服务器按 IP + 路由限流（默认 120 次/分钟，本机所有 bot 共用一个桶），本机同时跑两个快速 bot 会触发 429，api-client 重试 3 次后 runner 会强制提交当轮。这是环境问题，不是算法动作被拒；本机验证请用 `TACTICAL_GAME_RATE_LIMIT=1000000 npm run dev` 启动服务器。

## 使用方式

### 通过前端添加

1. 创建对局，选择同时回合模式地图（对峙之地 / 熔池王座）
2. 点击"添加 AI"按钮，切换到"算法脚本"标签
3. 下拉菜单选择"视界算法"
4. 点击"确定"

### 通过命令行运行

```bash
npm run dev  # 启动服务器

node algorithms/runner.mjs \
  --algorithm horizon \
  --url http://localhost:3100 \
  --game <gameId> \
  --token <playerToken> \
  --side player_a
```

### 通过 API 添加

```bash
curl -X POST http://localhost:3100/api/games/<gameId>/bots/algorithm \
  -H "X-Host-Token: <hostToken>" \
  -H "Content-Type: application/json" \
  -d '{"botType":"algo_horizon"}'
```

### 复现标定

```bash
npx tsx scripts/horizon-arena.mts --a horizon --b matrix-eq --map molten-throne --games 30 --seed-base 20261026
python rl/evaluation/evaluate_cross.py --player-a algo:horizon@v1 --player-b algo:kriegspiel@v2 --map standoff --games 2 --swap-sides --no-details
```

可调参数全部经环境变量 `HORIZON_*` 读取（见源码顶部 `PARAMS`），默认值即本档案的标定口径。

## 一句话总结

视界算法（horizon）把同时回合的每一份有序计划放进与引擎逐点一致的分步结算镜像里真打一遍，再把结算后的棋盘投影到终局——据点按到达时间、总部按两轮攻城压力、单位按下一轮威胁场——换算成胜率来挑计划，并用同构对手与对抗探针防止计划被一戳就破；在 3.8.2 真实引擎上对现有四个同时算法 240 局 236:4、零非法动作。
