## 定位

歼灭模式是「4 AP 逐人轮流 + 每两轮缩一圈炮火 + 军队打光淘汰」的 FFA。它有两个与标准模式不同的胜负轴：

1. **军力即分数**：歼灭图 `adjudicationWeights` 通常只有 `armyValue=2` / `killValue=0.5`（据点 / 补给 / 总部项为 0），所以「打掉一个重装」在裁决分上是断层，而不是线性交换；
2. **轮界会自然惩罚站位**：炮火每轮对危险区单位扣固定伤害（无视防御），站在预警圈里不走 = 白送军力。

本算法把这两条直接写进搜索与评估：动作按引擎顺序（移动 → 攻击/治疗/爆破）展开成候选，用裁决分差（我 − 最强对手）做叶值，扣炮火期望损失与暴露风险，再对决赛圈做一次「对手贪心回合 + 我」的 rollout。

与既有歼灭基线的差异：

| 维度 | random-annihilation | greedy-annihilation（评测基线） | **shrinkroll** |
|---|---|---|---|
| 选动作 | 随机合法动作 | 固定优先级：斩杀 > 治疗 > 补员 > 推进 | 束搜索（深度 ≤ 2×AP+2）+ 裁决分叶值 |
| 炮火 | 只避开非法部署/治疗 | 移动时避危险区（固定罚分） | 按 `artillery` 三式现算危险/预警圈，按军力折算期望损失 |
| 对手 | 无 | 无 | 领先者压制（我 − max 对手）+ 下一轮威胁折价 + rollout 对手贪心回合 |
| 多席位 | 无差异 | 无差异 | 3–6 人：领先者计满、次席按 `ACE_FFA_RIVAL=0.5` 折算，不做两两零和 |
| 确定性 | 随机 | 确定 | 确定（无 `Math.random`，候选排序用内容键 tie-break） |

## 通用性约束

- **不读地图身份**：源码不含 `mapId` / 地图名 / 坐标常量；兵种数值、AP、伤害/治疗方差、据点类型（收入 / 折扣 / `canDeploy` / 维修）、裁决权重、炮火参数全部从 `game.config` / `game.cells` / `game.controlPoints` / `game.units` 读取。**回合上限 `maxTurns` 已参与决策**（自实现迭代 v3 起建模，非注册版本：轮界按引擎顺序做据点流量累加 → 裁决判定 → 轮号 +1 → 炮火 tick，离上限不足 `ACE_ADJ_H` 轮时按趋势投影；`ACE_TURN_LIMIT=0` 回退到 v2 行为，仅供对照）。现行两图的标定里未见打到 `maxTurns` 的裁决局（历史记录为 19 轮内收场），所以这项只对随机图有可见影响（96% → 97%）。
- **零 import**：镜像与搜索全部自包含；对拍在测试里 import 真引擎，运行时不依赖服务端模块。
- **无隐藏信息**：只用 API 快照（`players` 只有公开状态与统计）；不读事件流、不推测对手计划。
- **只对合法动作负责**：找不到可用动作时返回 `null`（runner 结束回合），绝不抛异常。

## 决策流程

1. **建镜像**：`buildState` 复制单位（含 `hasMoved/hasActed/actionSpent`）、据点归属、补给、击杀分、**据点流量累加器**（`controlHold` / `controlHoldRounds`）、地形（`game.cells` + `map.terrainCells` 覆盖层），并按当前轮次现算 `safeRadius` / `danger` / `warning`（三式与 `src/engine/artillery.ts` 逐字一致）。
2. **候选生成**：
   - 攻击：所有「射程内 × 未 `hasActed`」，每单位取 `ACE_ATTACK_CANDS=4`，按斩杀概率与军力价值排序；
   - **集火宏**：对「2–3 次攻击可打死同一目标」打包成一条候选（`focus(target)`），整条线作为一条搜索边参与排序；
   - 移动+攻击：落点先满足射程，每单位取 `ACE_MOVE_ATTACK_CANDS=3`；落点排序把「能打到焦点敌」排在距离项之前；
   - 纯移动：每单位取 `ACE_MOVE_CANDS=5`，按「到焦点敌距离 + 危险/预警 + 可抢据点」排序；
   - 治疗 / 爆破 / 部署：分别按 `ACE_HEAL_CANDS=2`、1 个、`ACE_DEPLOY_CANDS=4` 剪枝。
   - **AP 门控**：`actionsUsed < actionsPerTurn` 才允许新激活；已 `actionSpent` 的单位免费跟进（移动后再攻击、攻击后再移动都只花 1 AP）。
3. **束搜索**：阶梯 `(B=2, 深 4) → (B=6, 深 6) → (B=8, 深 8)`，工作量用**确定性节点预算**封顶（两人局 260–700、多人局 320–620）；宽度 >1 的档位给「本回合已完成斩杀」的节点留 1 个保护槽。
4. **评估**：`A(s) = w_army·军力 + w_kill·击杀 + w_cp·据点 + w_sup·补给 + 补给影子价`（权重读本局 `adjudicationWeights`；影子价只对我方座位计价）；军力 = `Σ cost × hp/maxHp`（**不做**"被瞄准程度"的连续折价）；**据点项用引擎同式** `w_cp ×(flowRatio × controlHold + (1−flowRatio) × 持有数)`（流量口径，不是"当前持有数"），离回合上限不足 `ACE_ADJ_H` 轮时按当前持有趋势投影一次。`V = A(我) − R`（两人局 R = 最强对手；3 人以上 R = 领先者 + `ACE_FFA_RIVAL` × 其余对手合计），再扣炮火期望损失（含**未来 K 轮收缩投影**）与「对手一回合打死我」的离散风险。
5. **完整回合计划优先（仅两人局）**：`decide` 是纯函数（同一局面必然同一动作）。计划池里若存在「已走完整个回合」的计划，就只在其中挑首个动作——这样首拍的后续收益是真实可拿的，而不是"为一条可能走不完的链服务"。多人局不这么做（对手会插进来改局面，实测 3 人局第一名率会明显下降，掉到 81.7%）。另试过「多步计划按局面指纹缓存、下一拍直接执行计划下一步」的承诺式缓存：`trench-run` 能到 96.7%，但它让 `decide` 变成与历史相关的函数，踩掉「同局面同输出 / 同 seed 同序列」两条确定性契约，已移除。
6. **轮界建模**：`applyEndTurn` 在轮界按引擎顺序做「据点流量累加 → 回合上限裁决（`adjudicateAtTurnLimit`）→ 轮号 +1 → 炮火 tick」，所以搜索看得见"打到 `maxTurns` 按裁决分收场"，不再把裁决终局当不存在。
7. **rollout（两人局 H=1→2，3 人局 H=1）**：从决赛圈叶节点起，按名义顺序让其余座位各走一个贪心回合（束宽 1、最多 2 动作），再让我走一个，轮界炮火 / 淘汰真实结算。
8. **预检闸**：返回前用同一套镜像 `assertLegal` 再验一次；失败顺位下一候选；全部失败 → `null`。

## 参数与环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `ACE_BEAM` | `6` | 回合内束宽（阶梯末级再抬到 +2） |
| `ACE_ROLLOUT_H` | `1` | rollout 轮数；阶梯末级抬到 2（3 人局压到 1） |
| `ACE_ATTACK_CANDS` | `4` | 每单位攻击候选上限 |
| `ACE_MOVE_CANDS` | `5` | 每单位移动候选上限 |
| `ACE_MOVE_ATTACK_CANDS` | `3` | 每单位移动+攻击候选上限 |
| `ACE_DEPLOY_CANDS` | `4` | 部署候选上限 |
| `ACE_HEAL_CANDS` | `2` | 治疗候选上限 |
| `ACE_TAU` | `150` | 分差温度（保留给胜率换算，当前评估直接用裁决分差） |
| `ACE_BETA` | `0.1` | 两人局的风险系数：按「一个对手回合内被打死」的概率 × 单位价值计价 |
| `ACE_BETA_FFA` | `0.2` | 3 人以上的风险系数：多对手按 `1−Π(1−p)` 合成后会随人数放大，单起一档 |
| `ACE_SUPPLY_SHADOW` | `1.6` | 补给影子价（只对我方座位计价；歼灭图 `w_sup=0`） |
| `ACE_FFA_RIVAL` | `0.5` | 3 人以上局中"次席"在对手项里的权重（两人局数学上恒等价，不影响） |
| `ACE_ART_K` | `3` | 炮火前瞻轮数：投影未来 K 轮的安全半径（0 = 关闭）；投影夹到 `maxTurns`（`min(round+K, maxTurns)`），不投影引擎里不会发生的轮次 |
| `ACE_ART_W` | `0.4` | 前瞻罚项权重（1 = 未来每轮 tick 全额计价，实测会提前抢圈、放掉输出） |
| `ACE_ART_FINAL` | `0.25` | 终局安全半径 ≤1 时"站上最终安全格"的正向项系数 |
| `ACE_ADJ_H` | `3` | 裁决投影视界（离 `maxTurns` 不足这么多轮时按趋势投影据点流量） |
| `ACE_TURN_LIMIT` | `1` | 是否建模"打到回合上限按裁决收场"（0 = 回到 v2 行为，仅供对照） |

**两个概率口径分开**：`killProbability` 是**单刀**打死概率（攻击/斩杀排序用）；`multiHitKillProbability` 是**一个对手回合内**（最多 `actionsPerTurn` 刀、真实吸收态 DP）打死概率（风险项用）。风险按「一个对手回合内被打死」计价，残血更危险；多对手按 `1−Π(1−p)` 合成。

**工作量封顶（确定性）**：搜索用节点预算（两人局 260–700、多人局 320–620），rollout 只对每级决赛圈前 2 个节点做。用墙钟截断会让同一局面在忙/闲机器上给出不同动作（确定性用例在并行 CI 上会挂），所以宁可固定工作量。实测单次 decide（墙钟，bench 串行）：**4.91–10.85ms**（用例量 `min` / `median`，只作量级护栏，并行跑会整体抬高，不作性能验收）。

**消融开关（仅离线评测，不写进对外描述）**：`ACE_ABLATE` 逗号分隔。
`search`（束搜索退化为单步）、`rollout`（H=0）、`art`（炮火罚项置 0）、`idle`（空过回合罚项置 0）、`opp`（只关对手回合风险项：`P_expose=0`）。**语义变更**：v1 里 `opp` 是「`P_expose=0` 且 `surv≡1`」，v2 起连续的 `surv` 折价已整体删除，所以不再有 `surv≡1` 这一半。
所有开关只削弱评估/搜索强度，不影响合法性——消融版在自博弈里同样 0 非法动作。

> **v2 起 `surv` 连续折价已删除**，`ACE_ABLATE=opp` 的语义随之变化（现为只关 `P_expose`）；历史消融数字不可跨版本比较。下表是 S1 修复前的记录，且 `search` 消融现在连集火宏一起关，整表数字已过期，仅供追溯。

| 配置 | artillery-zone | trench-run | 说明 |
|---|---|---|---|
| 默认（全开） | 95.0%（57/60） | 93.3%（56/60） | — |
| `ACE_ABLATE=search` | 81.7%（49/60） | 90.0%（54/60） | 束搜索退化单步：**−13.3pp / −3.3pp** |
| `ACE_ABLATE=rollout` | 91.7%（55/60） | 95.0%（57/60） | 去跨回合投影：**−3.3pp / +1.7pp** |

| `ACE_ABLATE=idle` | 95.0%（57/60） | 88.3%（53/60） | 去空过罚项：**0 / −5pp** |
| `ACE_ABLATE=opp` | 95.0%（57/60） | 91.7%（55/60） | 去对手回合风险项：**0 / −1.7pp** |

**读法（如实记录）**：
- **历史数字不可直接跨版本比较**（语义变化见本节开头）：拿 v1/v2 早期那组 81.7% / 65.0% 出来对照时，它不是「现行默认的消融基线」，只是旧语义下的历史记录；上表全部在 v3 代码上重跑。
- 「去搜索反而更强」这个 v1 的老问题已经修掉：v1 时 `search` 消融在 trench-run 上是 **+15pp**（98.3% vs 83%），现在 az −13.3pp / tr −3.3pp。原因是 v1 的评估把补给当免费（部署压过攻击）又把军力按被瞄准程度连续折价，束搜索只是在放大这两处错价；修掉之后搜索才真正开始带来深度收益。
- **60 局样本的标准误约 ±3.4pp**：`rollout`（tr +1.7pp）、`idle`（az 0）、`opp`（az 0 / tr −1.7pp）这几格与默认在噪声内，不能当作"该项没用"的结论。被证实的命门是 **trench-run 上的炮火项（−20pp）** 与 **artillery-zone 上的搜索深度（−13.3pp）**。
- `idle` 两种口径都试过（"还剩 AP 就罚" vs 收紧成"还有能打的攻击才罚"）：tr 120 局 93.3% vs 91.7%，噪声内，最终保留简单口径；`ACE_ABLATE=idle` 现在 tr −5pp（v1 是 +3.3pp，"为了不罚随便走一步"不再复现）。
- 所有消融档 `illegalActions` 均为 0。

## 已知短板

1. **3 人局 90.0%（108/120）**：S1 把死亡风险改成「一个对手回合内被打死」后，同一风险系数下 3 人局一度掉到 66.7%——多对手按 `1−Π(1−p)` 合成会随人数放大惩罚，于是多人局单起一档 `ACE_BETA_FFA=0.2`（两人局仍 0.1），回到 90.0%。其余做法：多人局节点预算从 50–100 抬到 320–620、rollout 开到 3 人局（H=1）、`ACE_FFA_RIVAL=0.5`（次席不再不计分）。试过但没用的：预算 1200/3200、束宽 8、`ACE_FFA_RIVAL` 0.3/0.4/0.65/1.0；`ACE_BETA=0`（去对手风险）崩到 51.7%，说明风险项在 FFA 里是命门。完整回合计划优先只用在两人局（3 人局用它会掉到 81.7%）。**结论：还缺真正的多人对手模型（两个对手会互相打，也会一起打我）**，下一步该对"谁在打谁"建模，而不是继续调权重。
2. **trench-run 98.75%（158/160）**：v2 的差距在 16–18 轮的换血效率（输局兵力还领先却被打光）。v3 的终局收缩投影把这一项补上了：投影未来 3 轮的半径，只对"缩圈最终会盖满全图"（`minimumSafeRadius <= 0`）的图启用，权重 0.4。v2 试过但没用的手段记在这里备查：束宽 8、β 0.05/0.15、`ACE_SUPPLY_SHADOW` 0.8/1.0/2.4、moveAttack 候选 0/1、attackCands 6、moveCands 3、deployCands 2、rollout H=2、部署兵种按效率排序。
3. **对手模型只有一轮**：rollout 用贪心对手，识不破「诱我进 warning 圈」的陷阱。
4. **炮火只按期望损失**：不会主动把对手逼到外圈吃 tick；遇到同样重视轮界的对手会打成对拼。
5. **镜像漂移**：任何一条合法性漏项都会白丢整回合；靠 17 条对拍（含 `controlHold` 逐值对拍、炮火前瞻门控）+ 预检闸兜底。已知引擎事实：淘汰时单位被移出数组（3.8.11 起同时置 `alive=false`），镜像按「被淘汰座位的单位直接不存在」处理。
6. **6 人局只有自博弈与随机基线的证据**：32/32（100%），没有异质对手的强度结论。
7. **随机歼灭图 97.9%（47/48）**：48 局里输 1 局，且该图单独复跑 24/24 全胜，属随机对手的偶发；机制上已按引擎口径建模（流量 + 裁决投影）。

## 与规格不符的地方（逐条）

1. **补给影子价（规格没有这一项）**：`w_sup=0` 的图上「部署换军力」在裁决口径里是零成本，实测会把攻击挤出候选。v2 加 `ACE_SUPPLY_SHADOW=1.6`，且**只对我方座位**计价。这条不是裁决分，是决策辅助。
2. **军力不乘 `surv`（规格 §5.1 要求 `× surv`）**：连续折价在长廊图上系统性地奖励后撤（实测 −20pp），改为「一个对手回合内被打死」的死亡风险（`multiHitKillProbability`，多对手按 `1−Π(1−p)` 合成），两人局系数 `ACE_BETA=0.1`、3 人以上 `ACE_BETA_FFA=0.2`。
3. **`P_idle` 仍是"还剩 AP 就罚"**：规格写「仍有'有用动作'却结束回合的激活数」；按原意收紧的版本（只有还有能打的攻击才罚）实测 tr 91.7% vs 93.3%，噪声内且不更好，保留简单口径。
4. **`ACE_BEAM` 默认 6（规格给 4）**：v2 实测束宽 6 比 4 在 tr 上高 3.3pp，单次 decide 4.91–10.85ms 仍在预算内。
5. **`maxTurns` 裁决已建模（v3）**：镜像在轮界按引擎顺序做据点流量累积 → 裁决判定 → 轮号 +1 → 炮火 tick。现行两图的标定（vs random 480 局 + vs greedy 320 局）里未见打到裁决的局（所以这一项对它们没有分数影响），但随机图上它让搜索看得见终局（随机图 96% → 97%）。规格 §5.3 的「按趋势线性投影 `A` 到 `maxTurns`」只实现了据点流量与军力两项的近似，没有完整复刻裁决器。
6. **`ACE_MS` 已删除**：墙钟截断会让同一局面在忙/闲机器上给出不同动作（v1 的确定性用例在并行 CI 上真的挂过），工作量全部改成确定性节点预算。
7. **rollout 在 2–3 人局启用（v1 只在两人局）**：3 人局压到 1 轮（单次 decide 仍在 10.85ms 内）。
8. **集火宏 + 斩杀保护槽（规格没有）**：集火线在逐层按"单动作增量"排序时会被当成重复削血挤出 beam，所以打包成一条搜索边；beam 宽度 >1 时给"本回合已完成斩杀"的节点留 1 个槽。
9. **没有实现规格 §6 的"回合计划缓存"**：试过一版（局面指纹 + 预检闸），trench-run 能到 96.7%，但让 `decide` 不再满足「同局面同输出」，已移除；改为两人局「优先完整回合计划」（纯函数，tr 90.8% → 93.3%）。
10. **`decide` 把「移动+攻击」「集火宏」拆成两拍返回**：搜索里是一条边，输出时先交第一个动作，下一拍补后续（runner 一次只吃一个动作）。
11. **据点项已改成引擎流量口径（v3）**：`w_cp ×(flowRatio × controlHold + (1−flowRatio) × 持有数)`，镜像补了轮界累加器（与引擎逐值对拍）。此前"只数当前持有数"在 `controlPoint` 被随机放大的图上等于蒙眼。
12. **`ACE_TAU` 仍未参与**：评估直接用裁决分差，胜率温度留作后续标定。
13. **候选排序用内容哈希 tie-break**（不是 UUID）：UUID 会破坏同 seed 复现，纯字典序又会固定偏向某个兵种（v1 实测掉约 20pp）；比较用 UTF-16 码元（`compareTie`），不依赖 ICU/locale。
14. **镜像对 `intervalRounds` 做了 `max(1, trunc())` 防御**（引擎无此兜底），避免异常档除零；正常配置不可达。
15. **炮火前瞻是"门控 + 打折"的近似（规格没有这一项）**：只投影未来 3 轮、权重 0.4，且只在缩圈最终会盖满全图（`minimumSafeRadius <= 0`）时启用。全额前瞻（权重 1）在条带图上会提前抢圈、放掉输出（az 96.7% → 90%、3 人局 86.7% → 71.7%），这个门控是实测标定出来的，不是规格要求。
