## 算法原理

威胁感知算法属于经典的**效用驱动 AI**（Utility-based AI）与**影响图**（Influence Map）流派：把本回合所有候选动作（攻击/治疗/移动/部署/爆破）换算到同一效用尺度上，每步选全局效用最高的动作。它不做任何搜索或模拟，决策质量完全来自评估函数本身的两个信息结构：

1. **敌方威胁图**：对每个存活敌军预计算两组格子集合——
   - `immediate`（原地射程环）：敌人**站在原地**下回合就能打击的格子，确定性高；
   - `future`（机动后覆盖）：敌人经 BFS 可达格（∅ 平地、`moveRange` 内）再按射程环形展开覆盖的格子，需要"先移动再攻击"，确定性低。
2. **统一效用尺度**：1 点期望伤害/血量 ≈ 6 效用，其余所有收益（占领、治疗、推进、避险）按此校准，保证跨动作类型可比。

与另外两个算法的取舍正好互补：

| 算法 | 对手建模 | 前瞻推演 | 决策耗时 |
|---|---|---|---|
| greedy | 无 | 无（固定优先级） | <1ms |
| mcts | 无（单边推演） | 有（100 次模拟） | 0.5-1s |
| **threat** | **有（威胁图）** | **无（单步效用）** | **p50 0.25ms / p99 4ms** |

MCTS 的已知短板"走位暴露不会被惩罚，系统性高估推进类动作"正是 threat 的核心输入；而 threat 不推演对手回应链，则是与 MCTS 相反的取舍。

## 实现细节

### 核心参数

| 参数 | 值 | 说明 |
|---|---:|---|
| `DAMAGE_SCALE` | 6 | 1 点期望伤害/血量的效用 |
| `HEAL_SCALE` | 8 | 1 点恢复量的效用 |
| `THREAT_SCALE` | 0.8 | 1 点潜在承伤的效用损失（扫描后的平台区中值，见"性能表现"） |
| `IMMEDIATE_WEIGHT` | 0.85 | 原地即可打击的威胁权重 |
| `MOVE_ATTACK_WEIGHT` | 0.45 | 需先移动的威胁权重 |
| `volleys`（威胁截断） | = `actionsPerTurn` | 落点承伤只累加最强的 N 次打击，N = 敌方每回合行动点 |
| `LETHAL_PENALTY` | 0.8 | 威胁惩罚封顶 = 0.8 × 单位价值 |
| `OPPORTUNITY_DISCOUNT` | 0.75 | 走位后本回合可打出伤害的折扣 |
| `PROGRESS_SCALE` | 4 | 向目标推进 1 格的效用 |
| `MIN_ACTION_UTILITY` | 0.001 | 结束回合的效用门槛，**必须严格小于 `PROGRESS_SCALE`** |
| `CROWD_PENALTY` | 6 | 每多一个贴脸友军的扣分 |
| `DEPLOY_UTILITY` | 250 | 部署基准效用：最优动作不超过它时才补员 |
| `CP_BASE_UTILITY` | 60 | 占领据点基础效用（收入按据点 kind 取实际值） |
| `HQ_DAMAGE_BONUS` | 1.3 | 对敌方总部伤害项的压制系数（裁定按敌方 HQ 受伤计分 ×5） |
| 单位价值 | 120 + 3×cost | 击杀/阵亡/致命惩罚共用此尺度（infantry 255 / scout 234 / heavy 396 / ranger 354 / support 300） |

### 两个必须守住的约束（回归过，别再改回去）

1. **`MIN_ACTION_UTILITY` 必须严格小于 `PROGRESS_SCALE`**。`decide()` 返回 `null` 的语义是"结束整个回合"（见 `algorithms/lib/interfaces.mjs` 的 decide 循环），初版门槛取 4 正好等于"推进一格"的增量——于是"只能再接近目标一步"的整回合被直接掐掉。实测该门槛 4 → 0.001 让 vs greedy 胜率从 50% 升到 67%；提交版每 263 个回合里有 45 次是带着剩余行动点主动交回合的。
2. **所有动作生成必须按行动点预算门控**。引擎规则是每个单位每回合最多消耗 1 点（`validation.consumeAction`），已激活的单位再动是免费的。初版只给 `move` 做了门控，`attack/heal/demolish` 没做，实测 20 局里 15 局返回过 `action_limit_reached`，runner 遇错即 break，整回合剩余动作作废。统一收敞到 `canAct(unit, ctx)`。

### 威胁惩罚（连续化，非二值）

$$
\text{penalty}(u, pos) = \min\Big(0.8 \cdot \text{value}(u),\ \sum_{i=1}^{N} \text{threat}_i(u,pos) \cdot 0.8 \cdot (2 - \tfrac{hp}{hp_{max}})\Big)
$$

其中 $N$ = `actionsPerTurn`：把落点上各敌军的潜在输出从大到小排序，**只算敌方本回合真能开火的次数**。把所有敌军线性相加会凭空造出几倍火力，把所有落点的惩罚顶到封顶值、丢掉梯度，AI 就变成只会站着不动的怕死鬼——这正是在初版 2.2 权重下观察到的现象。

- 残血单位的"疲劳系数" `2 − hp/maxHp` 放大承伤恐惧：满血 ×1，半血 ×1.5，濒死 ×2
- 惩罚按单位价值封顶：威胁再高也不会超过"基本等于阵亡"的量级。实测**这个封顶是必要的**：在 2.2 权重下去掉它，vs greedy 从 15:15 掉到 9:11
- 移出敌人**当前**打击范围即可显著降罚（0.85 → 0.45 权重差），因此残血单位会优先脱离贴脸位置，哪怕仍在敌人机动覆盖内

### 各动作效用

1. **攻击**：`min(期望伤害, 目标血量) × 6 + 击杀奖励 − 反击风险`（对敌方总部伤害项 × 1.3 压制系数）
   - 稳杀（期望 − 掷骰下限 ≥ 血量）：击杀奖励全额（单位价值 / 总部 5000）
   - 大概率击杀（期望 ≥ 血量）：奖励 × 0.6
   - 反击风险：攻击者停留原地的威胁图取值，稳杀目标从威胁图中扣除（死人不会开枪）
2. **治疗**：`恢复量 × 8 + 危险队友加成`（队友正处威胁下时按其潜在承伤追加，治疗等于预支下回合的承伤）
3. **移动**：逐格评估取最优，与"原地"比较取增量：
   - 抢占中立/敌方据点：`60 + 收入 × min(剩余回合, 8) ×（敌方据点 ×1.5）`；接近回合上限（`maxTurns − 2`）时附加裁定分 +80。`maxTurns` 为 `null`（无回合上限）时按无限回合处理：收入仍按 8 回合封顶计价，终局 +80 永不触发
   - 走位火力投射：落点射程内最优目标伤害 × 0.75（本回合稍后即可兑现）
   - 落点威胁惩罚（见上）；向目标推进 `−距离 × 4`；友军扎堆轻微扣分（`CROWD_PENALTY`）；残血贴身治疗者 +25
   - 增量 ≤ 0 不生成动作；全局最优效用 ≤ `MIN_ACTION_UTILITY`（0.001）时才结束回合
4. **爆破**：效用 90，判据是"墙比脚下更接近目标"。早期还额外要求"墙后必是空地"，在隘口图上会让重装永不拆墙（实测 breach 图 0 胜 40 局）
5. **部署**：与战斗动作同一尺度比较（`DEPLOY_UTILITY` 250），且必须排在"无事可做"判定之前。触发条件仍与 greedy/mcts 一致（补给 ≥ 90 / 兵力不劣 / 据点 ≥ 2 / 第 8 回合起）。
   把部署排在判空之后会论为"兵力只减不增"：部队被全歼时 options 为空→直接 endTurn→永不补员（实测整局零动作、350 补给一分不花，会输给 random）

### 支援单位保排

support 的走位目标不再是敌方总部，而是最受伤的友军（无伤员时留守己方总部），配合高单位价值（300）带来的高威胁惩罚，支援单位自然保持在后排治疗位。

### 已知限制

1. **无前瞻**：单步贪心效用，不推演"我走这里→敌人打谁→我再怎么应"的回应链；多步战术（诱敌、卡位接力）超出能力
2. **小行动点预算的图会输**：`danger-close`（每回合 1 点、30 回合、两座 HQ 相距 4 格）实测只赢 18%——这种图上"一次走位 = 一整回合"，避险换不来 tempo，而固定优先攻击的 greedy 卡得更紧。同口径下 `multiplayer-ring`（每回合 7 点）只有 50%
3. **威胁图仍是近似**：已按 `actionsPerTurn` 截断求和，但仍假设每个敌军都选择打我（高估被集火概率），也忽略敌军之间路径互相阻塞的细节
4. **权重与地图尚未彻底解耦**：`DAMAGE_SCALE` 等仍是手工量纲。试过把 HQ 压制系数与据点基础分改为从 `adjudicationWeights` 推导，在内置图上无可测增益（desert 22:10 / 23:9 vs 21:11，32 局），danger-close 也照旧 6:26，故未采纳
5. **反击风险偏保守**：引擎允许同一单位"打完再走"（激活后移动不再耗行动点），而 `attackOptions` 只按停留原地计承伤，系统性低估攻击。试过取"原地与最佳撤离落点的较小值"，80 局对拍 38:42 无增益，故保留保守估计
6. **不做回合规划**：不会为"下一回合的斩杀组合"提前布局（这需要前瞻能力）
7. **多席位未标定（已知短板）**：所有权重的标定样本都是 2 人对局。3-4 人图上 threat 并不优于 greedy——
   multiplayer-ring 3 席位胜率 25%（两个 greedy 席位合计 37.5%）、four-corners 4 席位胜率 25%（与三个 greedy 持平）。
   两个直觉修法都已被数据否掉：把威胁截断上限按敌方席位数放大（3p 掉到 16%、4p 掉到 3%）、
   收紧触发条件的"回防拦截"（几乎不触发，各图战绩逐局不变）。真要修需要多席位专项建模（主要威胁判定、避免两线分兵）

## 性能表现

实测工具：`scripts/algorithm-arena.mjs`（headless 自博弈，直接驱动 `src/engine/`，不经 HTTP），每图 40 局、逐局交替席位，并审计每个动作是否被引擎接受。
对手 greedy 也已修正同类的行动点预算问题（同一个 bug 家族），否则它会因非法动作自损，战绩不可比。

### vs greedy（各图 40 局）

| 地图 | 修复版 threat | 初版 threat | 说明 |
|---|---:|---:|---|
| default | **38:2（95%）** | 16:24（40%） | 主图 |
| dual-lanes | **38:2（95%）** | 30:10（75%） | 双路 |
| breach | **35:5（88%）** | **0:40（0%）** | 拆墙判据修正前一场未赢 |
| forge | **31:8（80%）** | 16:24（40%） | 10 回合短图 |
| desert | **28:12（70%）** | 24:16（60%） | 无据点种类 |
| multiplayer-ring | 20:20（50%） | 22:18（55%） | 每回合 7 行动点 |
| danger-close | 7:33（18%） | 7:33（18%） | 每回合 1 行动点，已知短板 |
| **合计** | **197:82（70.6%）** | 115:165（41.1%） | 7 图 × 40 局 |
| random 地图（回合数/裁定权重随机生成） | 17:15（53%），32 局 | — | 鲁棒性抽查；权重随机化会摊薄优势 |

### 与其他算法

| 对手 | 战绩 | 备注 |
|---|---:|---|
| 初版 threat | **31:9（78%）**，40 局 default | 同口径直接对拍；初版即本文件修改前的工作区版本 |
| mcts | **14:6（70%）**，20 局 | 注意 mcts 的模拟用未播种随机数，批次间会飘（另一批 18:2）；另 mcts 对 greedy 约 5:15 |
| random | 24:0，24 局 | |

**分析**：

- 增益主要来自三处修复，而**不是**威胁图本身：行动点预算门控（41%→50%）、结束回合门槛（50%→67%）、威胁权重与火力上限标定（→约 75%）。
- 但威胁图确实有效：其余全同、只把 `THREAT_SCALE` 打到接近 0 的版本与之对拍 40 局，带威胁项的一边 26:14（dual-lanes）、24:16（breach），约 +10 个百分点；而权重取 2.2 时它变成负资产。
- 均分（裁定分）与胜率不一致要看清：threat 常靠"保兵力 + 抢点"拿到更高分，但淘汰多按 HQ 被磨平判负，所以过度保守会直接转化为败局。
- 对 RL 模型的同口径实测尚未进行。

## 决策时间

7008 次真实决策（dual-lanes、40 局）上的分布：

| 分位 | 耗时 |
|---|---:|
| p50 | 0.24 ms |
| p95 | 2.04 ms |
| p99 | 3.64 ms |
| max | 47 ms（后期大军叠加 GC 抖动，其他图未复现） |

单步典型耗时 0.25 ms，比 MCTS（0.5-1 秒）快三个量级：无搜索、无模拟，威胁图一次构建后全部查表。
新增的火力上限截断让 `threatAt` 每次查表要对命中列表排序（长度 ≤ 敌军数），实测代价可忽。
对局整体节奏由 REST 轮询间隔主导，算法本身不构成瓶颈。

## 优化方向

### 短期改进

1. **小行动点预算图的专项建模**：danger-close（每回合 1 行动点）只赢 18%，是目前最大的地图性短板。
   已被数据否掉的方向：把 HQ 压制系数/据点基础分改为按地图 adjudicationWeights 推导（无可测增益）、回防拦截逼近自家 HQ 的敌人（dual-lanes 反而 9:23）。
   缺的是一个"tempo 价值"量纲，而不是再调一个系数。
2. **一回合 Combo**：移动效用中计入"走位后本回合可斩杀"的全额价值（现已部分支持，可强化）
3. **对方部署感知**：把敌方部署点（据点）纳入威胁来源，提前布防
4. **参数搜索**：现有权重是人工扫描出来的，只扫了 `THREAT_SCALE` 一轴；应做网格/进化调参（算法锦标赛自动化）
5. **多席位口径**：内置图实测都是 2 人对局；3-4 人局（multiplayer-ring 设计为多方）的威胁图与结盟动态尚未验证

### 长期扩展

1. **浅层前瞻**：threat 评估作叶子节点 + 1-2 层对手回应搜索（threat 评估函数即天然的状态估值器）
2. **混合架构**：MCTS 用 threat 的威胁图约束采样（解决走位暴露问题）
3. **学习权重**：用对局记录回归校准效用权重

## 兼容性

- **支持模式**：仅标准模式（standard）
- **不支持模式**：歼灭模式（annihilation）、同时回合模式（simultaneous）
- **地图兼容性**：所有标准模式地图都能跑（含 random 地图，均合法完赛）。但强度与图相关：
  `danger-close`（每回合 1 行动点）与 `multiplayer-ring`（每回合 7 行动点）上会输给 greedy，实测见"性能表现"
- **席位兼容性**：2 人局已充分标定；**3-4 人局只保证动作合法、对局正常结束，不保证强于 greedy**（实测见"已知限制 7"）
- **运行环境**：Node.js ≥ 24，纯 JavaScript，无外部依赖

## 使用方式

### 通过前端添加

1. 创建对局，选择标准模式地图
2. 点击"添加 AI"按钮
3. 切换到"算法脚本"标签
4. 选择算法类型"威胁感知算法（Threat）"，AI 名称默认预填算法中文名，可自定义
5. 点击"确定"

### 通过命令行运行

```bash
npm run dev  # 启动服务器

# 另一个终端
node algorithms/runner.mjs \
  --algorithm threat \
  --url http://localhost:3100 \
  --game <gameId> \
  --token <playerToken> \
  --side player_a
```

### 通过 API 添加

```bash
curl -X POST http://localhost:3100/api/games/<gameId>/bots/algorithm \
  -H "X-Host-Token: <hostToken>" \
  -H "Content-Type: application/json" \
  -d '{"botType":"algo_threat"}'
```

## 代码结构

```javascript
// 评估核心
buildThreatZones()   // 威胁图：每敌军 immediate/future 两级格子集合，带火力上限与最小伤害
threatAt()           // 查表：某格潜在承伤，按 actionsPerTurn 截断求和
threatPenalty()      // 威胁 → 效用惩罚（残血放大、按单位价值封顶）
canAct()             // 行动点预算门控：未激活且无预算的单位不生成需耗点的动作
positionUtility()    // 位置效用：抢点 + 火力投射 − 威胁 + 推进 + 疏散 + 贴治疗（ownCells 显式传入）

// 动作生成
attackOptions()      // 攻击：期望伤害 + 斩杀奖励 − 反击风险
healOptions()        // 治疗：恢复量 + 危险队友加成
moveOptions()        // 移动：逐格评估与原地比增量
demolishOptions()    // 爆破：只拆确实更接近目标的墙
utils.deployDecision() // 部署候选（game-utils 公共实现，与 mcts 共用）：由 decide 按 DEPLOY_UTILITY 与战斗动作同尺度比较
buildContext()       // 整回合共用一份威胁图 / 目标表 / 行动预算 / 走位目标

// 导出接口
export default {
  name: 'threat',
  description: '威胁感知：威胁图统一效用评估，集火斩杀、避险走位、残血后撤',
  async decide(game, utils) { ... }
}
```

完整源码见 `algorithms/builtin/threat.mjs`（约 415 行）。

测试两份：

- `tests/algorithms/threat.test.ts`（15 场景）：稳杀集火、补刀、残血避险、治疗、抢点、部署、
  **行动点耗尽不得返回需耗点的动作**、**只能推进一格时不得提前交回合**、**被全歼后仍要补员**、
  火力上限截断（6 军与 14 军同决策）、拆墙判据正反例。
- `tests/algorithms/threat-selfplay.test.ts`：直接驱动引擎跑完整对局（default/breach/desert/dual-lanes/随机地图），
  断言 threat 席位 **零非法动作**、对局正常结束、开局无兵时也会补员。

## 一句话总结

Threat 用威胁图把"对手下回合能打我多疼"变成所有动作共用的一项效用，集火斩杀、残血后撤、走位避炮，单步决策 p50 0.25ms。
实测 7 图 280 局对 greedy 赢 70.6%（初版只有 41.1%）、对 mcts 14:6，是目前最强的内置算法 AI；
代价是不推演回应链，且在每回合只有 1 个行动点的图上仍会输给 greedy。
