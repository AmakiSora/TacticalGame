## 算法原理

前四个内置算法的共同点是**前向打分**：枚举这一步能做什么，给每个选项配一个效用常数，取最大。
`verdict` 反过来走——先回答"**这局我用哪条线赢**"，再从那个终局倒推回本回合每个单位该干什么。

### 第一步：裁决账本（所有动作第一次有了共同货币）

引擎的终局裁决分是可解析的（`src/engine/engine.ts` `scorePlayer`）：

```
total = 对敌总部累计伤害 × w.enemyHqDamage
      + 己方总部剩余血   × w.ownHqHp
      + 持有据点数       × w.controlPoint
      + 军队价值（造价×血量比） × w.armyValue
      + 补给 × w.supplies + 行动功绩
```

权重随地图变化（`default` 是 5/2/90/2/1，`danger-close` 是 20/1/30/1/0）。
本算法把**每一个动作都折算成它能改变多少裁决分**，于是攻击、占点、治疗、移动、部署第一次
在同一个"货币"里可比 —— 不是手工配的效用常数，是引擎的记分规则本身。几条直接掉出来的结论：

| 结论（default 图） | 算出来的值 |
|---|---|
| 游侠打敌方总部 38 血 | 38 × 5 = **190 分** |
| 同一炮打步兵 24 血 | 24 × 0.9 = **21.6 分**（差 9 倍） |
| 拿下一个中立据点 | **90 分** = 击杀一个满血步兵（2×45） |
| 部署一个步兵 | 花 45 补给（−45）换 45 造价的军队（+90）= 净 **+45** |

"打总部远比打单位值"不是一条写死的规则，是 `default` 图权重的读法；
换到 `danger-close`（20/1/30/1/0）同一套账本会自己得出"总部每一炮都值钱、单位不值钱"。

### 第二步：三条裁决线

| 线 | 条件 | 含义 |
|---|---|---|
| **斩首** `decap` | 排程算出能在剩余回合内把敌方总部打到 0 | 敌方总部归零 = 立即获胜，不参与打分 |
| **磨平** `wear` | 打不光，但磨得到分 | 总部伤害是裁决里权重最高的可累积项，换分也是赢法 |
| **裁定** `hold` | 守住现有分差到期末 | 宁可不打，不可亏分 |

### 第三步：反向排程（本算法的核心）

斩首线不是"往总部走"，而是一条**带期限的排程**。从"总部归零"这个终局倒推：

`siegeTimeline()` 逐回合推演一个微缩的攻城战 —— 每回合的行动点先供赶路单位移动
（每单位 1 个移动动作），剩下的给已到位的单位开火（单发伤害从高到低吃行动点），
直到累计伤害 ≥ 总部剩余血，得到**攻城回合数 `killRound`**。

```
slack = 剩余回合 − killRound
```

`slack` 就是 tempo 预算，它直接决定全军的风险姿态：

| slack | 姿态 | 行为 |
|---|---|---|
| ≥ 3 | `reserve` 储备 | 杀得完，不急着换命：风险折 1.35，路上顺手拿据点 |
| 0–2 | `press` 压上 | 刚好够，直线推进，容忍中等损失 |
| 打不光 | `trade` 磨平 | 改成"每点总部伤害值多少分"的交换账，风险折 0.65 |
| 敌方排程 ≤ 3 回合先拿下我方总部 | `rally` 全线回防 | 放弃进攻、放弃据点，全军压回总部 |
| 无威胁且分差为正 | `fortress` 守成 | 守据点、守总部，不主动接战 |

同一条排程反过来跑一遍敌方 → **敌人的斩首线**。四个已有算法都只看"我这步赚不赚"，
没有这一步。

排程是上界，但**不是无条件上界**：每单位按"路上要穿过几格敌方打击区"折算一个抵达概率
（`STEP_SURVIVAL^危险步数`）。不折损就会对着永远打不到的终点无限乐观。

### 第四步：tempo 量纲（`ALGORITHMS_NOTES` 点名的共同短板）

笔记里的结论是：threat 输 `danger-close`（1 行动点/回合，避险换不来 tempo，18%）、
field 输 `multiplayer-ring`（7 行动点，井外不存在，7%）—— **两者都缺"什么时候该接受亏损交换"**。

`verdict` 的三处回答：

1. **行动点预算进了排程**：`apPerRound = min(每回合行动点 × 席位数, 攻城部队数)`，
   赶路与开火争抢同一份行动点。`danger-close` 那种 1 AP/回合的图上，排程会自己算出
   "赶路都不够，很多回合只能走不能打"，不需要给短图单独写特判。实测该图 **24:6 / 21:9（75%）**，
   而 threat 在同图只有 18%。
2. **交换仲裁是算出来的**：打击分 − 原地承伤 × 姿态系数。进攻姿态把风险折到 0.65，
   于是"打一炮换一次挨打"自然划得来；储备姿态折到 1.35，宁可绕路也不换命。
3. **压力在失败前就被看见**：敌方排程给出的不是"谁在附近"，而是"还剩几个回合总部就没了"，
   于是 `rally` 会在失去胜势**之前**触发。

### 与既有算法的范式差异

| 算法 | 决策结构 | 时间结构 | 对手建模 |
|---|---|---|---|
| greedy | 固定优先级阶梯 | 无 | 无 |
| mcts | 前向采样搜索 | 有（模拟深度 8） | 隐式 |
| threat | 单步效用（逐项手工量纲） | 无 | 有（威胁图） |
| field | 连续势场取梯度 | 无 | 有（斥力井） |
| **verdict** | **先选胜线，再倒推期限** | **有（攻城排程 + 期限）** | **有（敌我双向排程）** |

## 实现细节

### 核心参数

| 参数 | 值 | 说明 |
|---|---:|---|
| `KILL_TEMPO` | 0.5 | 击杀的额外分：目标不只是一坨血量，还持续输出 |
| `HQ_KILL_POINTS` | 1e6 | 斩首不是分数，是胜利本身 |
| `PACE_POINTS` | 5 | 每步推进的分数下限 |
| `MIN_POINTS` | 0.001 | 结束回合门槛，**必须远小于 `PACE_POINTS`** |
| `STEP_SURVIVAL` | 0.55 | 单步穿越敌方打击区的存活率（标定见下） |
| `MIN_ARRIVAL` | 0.1 | 抵达概率下限 |
| `RESERVE_SLACK` | 3 | slack ≥ 该值 → 储备姿态 |
| `EMERGENCY_ROUNDS` | 3 | 敌方排程 ≤ 该回合数 → 全线回防 |
| `MAX_SIEGE_ROUNDS` | 40 | 攻城排程的推演上限 |
| `DEFEND_HORIZON` | 3 | 回防到位收益按"挡住敌方几个回合的炮火"计价 |
| `EXPOSED_CP_RISK` | 0.6 | 守成线上据点/兵力被刮走的摆动系数 |
| `GARRISON_POINTS` / `CROWD_POINTS` | 40 / 6 | 驻守己方据点 / 贴脸拥挤 |
| `OPPORTUNITY_DISCOUNT` | 0.75 | 走位后本回合可兑现火力的折扣 |
| `DEPLOY_PRIORITY` | 1.5 | 部署门槛 = 部署净收益 × 该系数 |
| `DEMOLISH_POINTS` | 60 | 拆一堵墙换来的推进 |
| 姿态风险 / 占点 / 急迫 / 接战 | 见源码表 | 依次为 `POSTURE_RISK` / `_CAPTURE` / `_URGENCY` / `_OFFENSE` |
| 单位价值 | `w.army × 造价` | 击杀/阵亡/封顶共用（与引擎 `armyValue` 同式） |

`STEP_SURVIVAL` 的标定（vs greedy，7 图 ×30 局合计胜率）：

| 取值 | 合计 |
|---|---:|
| 0.72（初版） | 89.0% |
| 0.62 | 92.4% |
| **0.55** | **95.7%** |
| 0.45 | 回落（multiplayer-ring 100%→60%） |
| 0.35 | 进一步回落（default 73%） |

再往下排程会过度悲观、斩首线永不触发，全落到磨平线上硬换。

### 十个必须守住的约束（都踩过，别再改回去）

1. **结束回合门槛必须极小**。`decide` 返回 `null` 的语义是"结束整个回合"，门槛一旦接近
   `PACE_POINTS`，只能再走一格时会被直接掐掉回合（与 threat/field 同源的陷阱）。
2. **所有耗行动点的动作必须过 `canAct` 门控**。runner 遇错会 `break` 掉整个回合、作废剩余行动点。
3. **部署判定必须排在"无事可做就结束回合"之前**。否则部队被全歼或全员已行动完时
   `options` 为空会直接 `endTurn`，退化成"兵力只减不增"。
4. **"已经到位"（剩余步数 0）那一档的推进梯度必须归零**。用 `到位收益 ÷ 剩余步数`
   会在剩余步数 0 时报出"再进一格 = 整个到位收益"，远程兵于是继续贴脸，
   甚至放下已经够到的打击去走一格挣这份假梯度（实测：游侠放着 **111 分**的总部打击不打，
   去走一格挣 **133 分**）。
5. **不能顺手把推进梯度改成调和衰减**。看着更"正确"（边际递减），但远处梯度会衰减到
   几乎与 `PACE_POINTS` 同量级，长图上部队走不动：breach 100%→57%、dual-lanes 93%→57%。
6. **打击选项必须扣"原地承伤"**。开火意味着这个回合就停在原地，承担敌方下一轮全部火力。
   不扣这一项，算法会在隘口把整支军队换光 —— 打一炮的成本被当成 0，而撤退的收益仍在，
   于是"反正躲不掉，不如打"退化成"主动走进躲不掉的位置"：dual-lanes 93%→60%。
7. **打击选项必须另加"暴露下降"差分**。打死的人下回合不再开枪，这一炮确实让自己更安全。
   没有它，"集火斩杀"就只是多打掉几十点血，永远打不过"撤到安全格"（46.8 分 < 56.4 分）。
   注意是差分 `before − after`，不是再扣一次完整风险（第 6 条已经扣过了）。
8. **攻城排程必须按抵达概率折损**。不折损的排程会对着永远打不到的终点无限乐观：
   dual-lanes（双路夹墙，走廊被对面火力全覆盖）上排程恒报"3 回合可破"，
   整局往绞肉机里填人，胜率 53%（折损后 83%，再配合第 6 条到 93%）。
9. **回防目标必须有自己的到位收益**。只给 `PACE_POINTS` 的话，"回家"就是一个 5 分/步的平坡，
   任何一点路过的风险都能把单位推离自家总部 —— 守成线变成"绕着老家兜圈子"
   （实测：紧急回防时单位反而退了 3 格）。
10. **守成/回防姿态下必须压低接战倾向**（`POSTURE_OFFENSE`）。否则单位为了挪到"好火力位"
    会放弃任务：实测紧急回防的步兵为了挪到敌方总部隔壁（机会火力 90 分）而不回家。

### 已知限制

1. **对上 threat 时 forge 只有 33%**（同一张图 verdict 打 greedy 是 100%、threat 打 greedy 是 80%）。
   `forge` 是半径 6、10 回合的短图，双方都必须抢 tempo；threat 的单步效用在这种
   "每一步都要兑现"的图上不会被排程的长期乐观拖慢。这是目前最明确的相克关系。
2. **4 人局弱于 2 人局**：`four-corners` 4 人 20 局只赢下 2 个席位局（10%），
   而 greedy 每个席位 30%。根因与 threat/field 相同 —— 全部权重在 2 人对局上调出，
   `siegeTimeline` 对多席位敌人只做线性叠加，没有"主要威胁/结盟"判断。
   本算法**被全歼/多线压力下**的表现在多人局未标定。
3. **`random` 地图只有 60%**（30 局）。裁定权重与回合数被随机化后，
   "用哪条线赢"的判定会摇摆（threat 同口径 53%、field 40%）。
4. **相对最弱的一图是 `danger-close`**：45/60（75%）。它同时也是唯一对两个对手都赢的图
   （threat 30:0、field 30:0），但打 greedy 时波动明显比别的图大。
5. **排程仍是乐观模型**：抵达概率是按环距比例估的，不建模"敌人会主动拦截这条路线"；
   每个回合重算一次，靠逐回合重规划自我修正。
6. **客户端视角看不到 `stats.headquartersDamage`**（`sanitizeGameForResponse` 只给快照，
   不含 `players[].stats`）。算法用"敌方总部掉了多少血"替代：2 人局两者完全相等；
   3-4 人局是"我方贡献"的上界（别人打的也算在我头上），会让多人局高估自己的分 —— 方向一致，
   只影响选线的激进程度，是限制 2 的一个成因。
7. **单步执行**：排程是"整回合交付"级的推演，但实际动作仍由 `decide` 逐个返回；
   本回合的走位只按当前姿态的梯度走，不会为了两条线之间的切换做提前量。

## 优化方向

### 短期改进

1. **`forge` 对 threat 的相克（最大短板）**：需要 tempo 的"兑现速度"量纲 ——
   短图上"每一步都得换成伤害"，而排程天然是按回合摊销的。
2. **多席位威胁判定**：3-4 人局需要"主要威胁/结盟"识别，否则两张排程把所有敌人等价叠加。
3. **排程的拦截建模**：目前抵达概率只看"这条路线上有多少格被覆盖"，
   不看"敌人会不会主动堵这条线"。叠一层敌方走位预测即可，但要防过度悲观。
4. **`random` 地图鲁棒性**：60%。裁定权重随机化后"哪条线赢"的判定需要更稳的
   置信区间，而不是单点估计。
5. **参数搜索**：`STEP_SURVIVAL` 已做过一维扫描，`POSTURE_*` 四张表仍是人工配的，
   竞技场已具备自动对拍能力，可做网格/进化调参。

### 长期扩展

1. **排程 → 计划**：现在排程只产出"还差几个回合"，可以让它同时产出"哪个单位在第几回合
   到位哪个格子"，变成一份真正的作战计划（对应"指挥官剧本"范式的第一步）。
2. **线的动态切换**：现在每条线内部姿态不变，可以按每回合的实际兑现速度
   （实际总部伤害 vs 排程预测）动态修正 `slack` 的置信度。
3. **浅层反制**：用裁决分做叶子估值，叠 1–2 层"我走这里 → 敌人最优回应"的搜索。

## 兼容性

- **支持模式**：仅标准模式（standard）
- **不支持模式**：歼灭模式（annihilation）、同时回合模式（simultaneous）
- **地图兼容性**：所有标准模式地图都能跑（含 random 地图，均合法完赛）；强度与图相关，见上表
- **席位兼容性**：2 人局已标定；3-4 人局只保证动作合法、对局正常结束，不保证强于 greedy
- **运行环境**：Node.js ≥ 24，纯 JavaScript，无外部依赖

## 代码结构

```javascript

hqDamageDealt()        // 客户端视角下"对敌总部的累计伤害"（用总部掉血近似）

riskyShares()          // 按环距统计"多少比例的格子落在敌方打击区内"
siegeTimeline()        // 攻城排程：行动点先赶路后开火 → killRound（按抵达概率折损）
riskySteps()           // 一段路程预计穿过几个危险格 → 抵达概率

// 选线与姿态
accessibleSwing()      // 敌方还能从我现在分上刮走多少（守成线的悲观下界）

// 估值与动作
unitWorth() / hpWorth() / riskPoints()   // 裁决分计价
incomingAt()           // 落点期望承伤（按敌方出手上限截断，可排除将被击杀的目标）
strikePoints()         // 一次打击的裁决分：打单位 = 血 × 军队价值/最大血；打总部 = 血 × w.hqDamage
bestStrikeFrom()       // 某落点本回合能兑现的最高打击分
missionPayoff() / paceGradient()   // 任务推进的到位收益与每步梯度

positionPoints()       // 落点评分：占点 + 机会火力 − 风险 − 推进 − 扎堆 − 驻军
strikeOptions()        // 打击：打击分 − 原地承伤×姿态 + 暴露下降差分
healOptions()          // 治疗：回复量 × 军队价值/血
moveOptions()          // 移动：逐格"落点评分"取最优，与原地比较取增量
demolishOptions()      // 爆破：只拆比脚下更接近任务目标的墙
buildContext()         // 整回合共用：权重、敌情区、排程结果、任务目标、梯度

// 导出接口
export default {

  description: '裁决线：从终局倒推攻城排程与期限，全动作按裁决分计价',
  async decide(game, utils) { ... }
}
```

## 一句话总结

`verdict` 不评估"这一步好不好"，而是先用引擎的裁决权重当账本选出"这局我用哪条线赢"，
再从"敌方总部归零"这个终局逐回合倒推出一条带期限的攻城排程，用 `slack` 决定全军的风险姿态；
7 图 30 局对 greedy **201:9（95.7%）**、两套种子一致，对 threat 76.7%、对 field 88.6%、对 random 24:0，
在 `danger-close`（threat 18%）与 `multiplayer-ring`（field 7%）两个老短板上都是三者中最强的；
代价是对上 threat 时 `forge` 只有 33%，以及 4 人局仍然未标定（10%）。
