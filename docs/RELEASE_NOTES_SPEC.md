# RELEASE_NOTES 编写规范

本文档规定 `RELEASE_NOTES.md`（版本迭代日志）的版本号与条目写法。目标：发版时只花几分钟写清「上一版 → 本版」的对外变化，实现细节留给专题文档。

## 1. 版本号

遵循[语义化版本 2.0.0（中文版）](https://semver.org/lang/zh-CN/)：`X.Y.Z`，X/Y/Z 为非负整数且不补零。

- **破坏性变更** → 递增 X，Y/Z 归零；
- **向下兼容的功能新增** → 递增 Y，Z 归零；
- **修复、样式/文案/平衡性调整、内部改进** → 递增 Z。

对外契约包括 REST 接口、SSE 事件 schema、持久化与回放格式、`skill/` 协议、前端页面入口与共享模块接口。已发布的小节不可修改；需要更正说明时发下一版。本项目自 1.0.0 起即为正式版本，不使用 `0.y.z`。

## 2. 小节结构

版本按倒序排列，标题固定为 `## x.y.z`（`script/bump-version.mjs` 依赖该格式插入占位），分类顺序固定：

```markdown
## x.y.z

### 新增
- ...

### 变更
- ...

### 修复
- ...

### 移除
- ...

### 测试与验证
- ...
```

只保留有内容的分类。新增 = 新功能/模块/页面，变更 = 既有行为调整，修复 = 缺陷修正，移除 = 能力下线，测试与验证 = 测试与端到端结论。分类按条目的**主导效果**归位，一条只进一个分类；破坏性变更条目前加「**破坏性变更**：」。

## 3. 写法：简洁优先

- **一条一主题，最多两句**：第一句写结论与影响，第二句给关键数值或链接；默认不超过 120 字。
- **细节外链**：算法、模型、架构、跑批过程写专题文档，日志只留摘要 + 链接，不复制实现细节。
- **测试汇总**：每版最多 3 条，写新增测试概况、关键端到端验证、`npm run build` / `npm test` 结果；不逐条列用例名与断言。
- **只写对外变化**：读者视角是「上一版本 → 本版本」；开发分支上的返工、内部调整、措辞更名不写。
- **保留必要可追溯性**：只保留关键路径与数值，不重复 README、算法档案或统计页已有内容。
- 版本号提升本身不单独立条，除非带来值得说明的行为变化。
- 历史小节保持原样，不按新规范回改。

## 4. 发版流程

1. 在 `release/x.y.z` 分支执行 `npm run version x.y.z`，同步全部版本引用并插入占位小节。
2. 按第 3 节补全小节；通常 3–7 条即可。
3. 运行 `npm run check-version`、`npm run build && npm test`。
4. 已发布内容不再修改；下一版再记录新的变化。

## 5. 历史说明

3.0.0 起的小节已按原分类规范整理。3.x 的历史版本号沿用发布时的实际编号——其中部分含功能新增的版本使用了修订号位（例如 3.2.2 新增歼灭模式、3.4.1 新增随机地图系统），按现行规则应记为次版本号；为保持既有引用与阅读习惯，历史编号不回改。

3.0.0 之前的 1.x / 2.x 小节归档在 [`docs/release-notes-archive.md`](release-notes-archive.md)，主文件只保留 3.x 及之后。归档内容保持原样，不按新规范回改，也不参与版本号提升；新增版本仍写入主文件。
