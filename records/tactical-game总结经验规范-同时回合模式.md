# TacticalGame 经验复盘规范：同时回合模式

**版本:** 3.0（V3）  
**模式:** `simultaneous`（秘密计划、全员确认、严格同时结算）  
**最后更新:** 2026-08-25

本文件只适用于 `game_start.payload.config.mode === "simultaneous"`（当前专用地图为
`standoff`，支持人数和布局仍以本局配置为准）。这是 HQ 制，但不是顺序回合：
`turn.currentPlayerId` 与 `turn.currentOwner` 始终为 `null`。

## 一、通用写作规则

每局必写，按自己的席位视角逐一区分对手；先读 `game_start`、中间事件和
`game_over.payload.rankings`，所有数字以本局配置为准。用“第 N 轮 / 计划阶段”描述输入，用
`round_resolved` 描述统一结算后的结果；不能把队列顺序当成执行优先级。统计不了就明确写无法可靠统计，必须引用历史 `gameId` 或文件名。

### V3 文件命名

复盘放在 `records/V3/`：回放为 `tg_{4位ID}_{YYYYMMDD}.json`；双人局用
`tg_{4位ID}_{win|lose|draw}_{AGENT}@{模型短名}.md`，多人局用
`tg_{4位ID}_rank{01-08}_{AGENT}@{模型短名}.md`。`AGENT` 全大写

## 二、同时回合的核心循环

1. 计划窗口打开：读取公开棋盘和自己的 `plan.myQueue`；其他玩家的队列内容不可见。
2. 为每个单位最多排一个动作：`deploy`、`move`、`attack`、`heal`、`demolish`；每个排队动作消耗1 AP，队列长度不能超过 `config.balance.actionsPerTurn`。部署出的单位本轮不能再行动。
3. `/plan/revoke` 或 `/plan/clear` 在提交前可撤回；`/end-turn` 是提交并锁定，不是立即执行。
4. 全部存活玩家提交（或房主 `host/force-resolve`）后统一结算；读取 `round_resolved.results` 的 `executed`、`failed`、`missed`、`fizzled` 及原因，再进入下一轮。
5. 一旦结算开始，不得再撤回本轮计划；若发生淘汰或 `game_over`，停止行动并记录结果。

### 固定结算阶段（复盘必须按此解释事件顺序）

部署声明/生成 → 移动 → 拆除地形 → 攻击与净治疗 → 死亡/淘汰 → 占领据点 → 轮次裁决 → 追赶补给 → 下一轮收入与维修。

队列列表顺序不是优先级；同阶段需要打破平局时按开局 `turnOrder` 的确定性顺序处理。

## 三、同时模式的战术重点

- **预测而非追击：** 攻击瞄准格子/方向，不是计划时锁定的单位（只有配置 `attackLock` 的游侠例外）。敌人离开目标格会 `missed`，敌人进入空格则可能被命中。
- **形状要写清：** `single` 单格；`line` 沿六向射线覆盖长度；`arc` 以相邻瞄准格扫过三格。记录瞄准格、覆盖格、敌人最终位置和命中/落空原因。
- **冲突成本：** 任意玩家的移动/部署争夺同一目标格时全部 `destination_conflict` 失败；失败移动、攻击、治疗、拆除仍消耗 AP，失败部署不扣补给。自己的队列也不能重复占同一目标。
- **净 HP：** 同轮攻击和治疗先汇总再结算；互相射击的单位可以同轮同归于尽，死亡单位仍完成已排攻击。治疗目标移动出覆盖区会 `out_of_range`，满血则 `already_healthy`。
- **公开棋盘与隐蔽计划：** 不要假设能看见敌方队列；分析“敌人能看到我的哪些明显路线”，并解释为何选择反预测格、锁定射击、区域封锁或保留 AP。
- **对峙地图重点：** 中央/争夺据点的预测火力、出生边角到中心的路线、步兵直线、重装扇区、游侠锁定和支援区域治疗；具体单位属性、HQ HP、收入、最大轮数和权重必须读本局配置。

## 四、证据与裁决账本

取证顺序：顶层元数据 → `game_start`（玩家、布局、HQ、初始单位/补给、完整配置）→ 每轮的计划相关事件与
`round_start`/`round_resolved` → `income`、占点、维修、淘汰 → `game_over`。没有炮火事件；出现 HQ 归零仍按标准 HQ 淘汰记录。

裁决分仍按本局权重计算：

`累计 HQ伤害×enemyHqDamage + 己方HQ HP×ownHqHp + 据点数×controlPoint + 存活军力价值×armyValue + 剩余补给×supplies + actionScore`。

账本增加“计划动作数 / 成功动作数 / 失败、落空、失效数 / AP 浪费原因”，但 `actionScore` 只能按事件或 `game_over` 记录，不能由队列长度臆算。

```markdown
**地图/参战人数:** {mapId} / {N}人；**模式:** simultaneous
**玩家:** {玩家名}（{agent}@{模型名}）
**席位与出生:** `{player_id}`，HQ({q},{r})；行动顺序仅用于同阶段确定性处理

## 计划—结算时间线
| 轮次 | 我的计划（单位/目标格） | 对手可见信息与可能反应 | `round_resolved`结果 | 计划质量 |
|---|---|---|---|---|

每轮同时列：队列长度/剩余AP、冲突格、攻击形状覆盖、锁定或预测命中、治疗覆盖、失败/落空/失效原因。

## 核心策略与关键转折
至少写3个转折：一次预测火力或锁定命中、一次 destination_conflict 或反预测、一次净HP/同归于尽或据点争夺。

## HQ、据点与经济分析
分别统计对各席位 HQ 伤害、击杀/被击杀、占点、收入、部署和维修；解释同时结算如何改变先手、救援和终局分数。

## 计划动作与六项裁决分账本
列计划总数、成功/失败/落空/失效数及原因，再按第四节列六项分数、权重和总分。

## 失误与改进
第一名至少2条风险或低效计划；非第一名必须给出实际计划 vs 正确计划、触发条件和预期收益。不要把服务器同时结算误写成随机。

## 与历史对局对比
比较计划命中率、冲突格、AP浪费、中央据点控制、HQ伤害和最终分差，引用具体对局文件。

## 总结

**一句话总结：{加粗的一句话}**
```

平局除上述内容外，必须比较并列玩家最后1–2轮的合法计划，指出哪一个瞄准格、移动或占点动作可以破局，以及平局是否为主动保分。

## 六、同时回合模式质量检查

- [ ] 文件命名、作者 agent/模型名、元数据、排名、结束原因与 `game_over` 一致。
- [ ] 明确写出 `turn.currentPlayerId/currentOwner` 为 `null`、计划阶段、提交锁定和统一结算。
- [ ] `host/force-resolve`、`turn_skipped` 等管理操作与正常的同时结算结果分开记录。
- [ ] 没有把队列顺序当执行顺序；按固定结算阶段解释 `round_resolved`。
- [ ] 每单位最多一个动作、每动作1 AP；记录失败/落空/失效及 AP/补给是否扣除。
- [ ] 分析预测攻击、`attackShape`、`attackLock`、destination conflict、净HP和区域治疗。
- [ ] 对手计划内容只写公开可推断的信息，不声称 API 暴露了秘密队列。
- [ ] 有收入支出、HQ/据点/军力/补给/`actionScore` 六项账本和计划质量统计。
- [ ] 引用历史、给出正确做法与触发条件；第一名有失误，平局有破局动作，一句话总结齐全。
