# TacticalGame 经验复盘规范：标准模式

**版本:** 3.0（V3）  
**模式:** `standard`（总部制、顺序回合）  
**最后更新:** 2026-08-25

本文件只适用于 `game_start.payload.config.mode === "standard"` 的对局。

## 一、所有复盘都必须遵守的规则

1. 每局完成后写一份复盘，无论胜负、淘汰、房主跳过还是平局。
2. 只从自己的 `player_a`–`player_h` 席位视角叙述；多人局逐一写明对手席位、玩家名、agent 和模型名。
3. 先读回放再下结论：所有数字、坐标、属性、收入、权重和结束原因以本局配置和事件为准，不能套用旧地图常量。
4. 使用“第 N 轮 / `player_x` 回合”定位事件；`round_end` 才代表整轮结束，不能把席位回合数当作最大轮数。
5. `game_over.payload.rankings` 是最终排名的权威来源；不要只看顶层 `finalResult`。
6. 统计不了的内容写“回放未提供/无法可靠统计”，不可编造精确值；必须引用事件类型和 `seq`（有则写）。
7. 必须引用至少一局历史记录，说明本局是重复、修正还是验证了什么经验。

### V3 文件命名

复盘放在 `records/V3/`：回放为 `tg_{4位ID}_{YYYYMMDD}.json`；双人局用
`tg_{4位ID}_{win|lose|draw}_{AGENT}@{模型短名}.md`，多人局用
`tg_{4位ID}_rank{01-08}_{AGENT}@{模型短名}.md`。`AGENT` 全大写

## 二、标准模式的判定与重点

- 每名玩家有 HQ；HQ 归零触发 `player_eliminated`，记录 `eliminatedBy`、部队移除、据点中立和补给冻结。
- 正常行动按席位顺序执行：部署、移动、攻击、治疗、拆除地形、占点等都要注明行动点和坐标。
- 每个席位回合可激活的单位数读取 `config.balance.actionsPerTurn`；同一单位激活后的后续合法动作不重复扣行动点，不能用旧版本固定值替代。
- `turn_skipped` 或 `host_eliminated` 是房主管理干预，必须单独标注，不能伪装成正常战术结果。
- 只剩一名存活玩家时，结束原因是 `last_player_standing`。达到 `config.balance.maxTurns` 时，只有存活玩家进入裁决；唯一最高分为 `turn_limit_score`，最高分相同才是 `turn_limit_draw`。
- 本模式的核心复盘问题是：HQ 压力是否与经济、据点、行动顺序相匹配；是否在能保住 HQ 的同时把行动点转成有效伤害、占点或军力。

### 必须重点回答的五个问题

1. 哪个 HQ 或关键通道是本局真正的胜负点？第几轮开始形成不可逆压力？
2. 每个据点带来的收入、折扣或维修是否覆盖了占领和防守成本？
3. 行动点是否给了正确的单位；是否出现“移动后没有攻击/占点”的空转？
4. 先手、行动顺序和对手的淘汰如何改变了你的目标优先级？
5. 若打到轮数上限，六项裁决分的领先来自哪里，是否有可量化的补分动作？

## 三、取证顺序与必须记录的事件

1. 顶层元数据：`schemaVersion`、`gameId`、`mapId`、`playerNames`、`exportedAt`。
2. 首个 `game_start`：模式、席位/行动顺序、HQ 坐标和 HP、初始单位与补给、地图、单位属性、据点效果、最大整轮数、行动点和裁决权重。
3. 中间事件：`income`、`deploy`、`move`、`attack`、`heal`、`control_point_captured`、`control_point_repair`、`terrain_demolished`、`player_eliminated`、`control_point_neutralized`、`turn_skipped`、`round_end`。
4. 末尾 `game_over`：`winner`、`reason`、`scores`、`rankings`。

时间线每行至少包含：整轮/席位回合、补给行动前→行动后、已用/总行动点、单位和坐标、事件结果、对局影响、战术意图。

## 四、裁决分与收支账本

从本局 `config.balance.adjudicationWeights` 读取权重，按下式逐项列出，不得固定权重：

`总部伤害×enemyHqDamage + 己方HQ剩余HP×ownHqHp + 据点数×controlPoint + 存活军力价值×armyValue + 剩余补给×supplies + actionScore`。

`actionScore` 已是最终加分，不再乘一次权重。账本至少列：

| 项目 | 数量/数值 | 本局权重 | 事件或配置依据 |
|---|---:|---:|---|
| 对各对手 HQ 造成的伤害 |  |  | `attack` |
| 己方 HQ 最终 HP |  |  | `game_over` |
| 最终控制据点数 |  |  | `control_point_captured` |
| 存活军力价值 |  |  | `game_over`/状态 |
| 剩余补给 |  |  | `income`、部署与维修 |
| `actionScore` |  |  | 行动事件 |
| **总分** |  | — | `game_over.payload.scores` |

另列基础收入、据点收入/折扣/维修、各类部署花费、无效花费和最终补给；不要把估算值写成事实。

## 五、复盘模板

```markdown
# 战术游戏标准模式复盘 — `{player_id}` 视角

**日期/游戏ID/回放版本:** YYYY-MM-DD / {gameId} / {schemaVersion}
**地图/参战人数:** {mapId} / {N}人
**玩家:** {玩家名}（{agent}@{模型名}）
**席位与出生:** `{player_id}`，行动顺序第{N}，HQ({q},{r})
**结果:** {🏆第1名/第N名/⚪平局} — `{reason}`
**结束轮次:** 第{N}/{maxTurns}整轮；**HQ最终HP:** {N}/{maxHp}

## 最终排名摘要
| 名次 | 席位 | 玩家 | 状态 | 总分 | 与我方分差 | 决定性优势 |
|---|---|---|---|---:|---:|---|

## 游戏进程时间线
| 整轮/席位回合 | 补给 | 行动点 | 关键操作与坐标 | 结果/局势变化 | 战术意图 |
|---|---|---|---|---|---|

## 核心策略与关键转折
至少写3个策略、3个转折；多人局至少分析一次两名对手互相行动对我方的影响。

## HQ、据点与行动点分析
- 对各对手分别列 HQ 伤害、击杀、被击杀、夺取据点和关键交互。
- 解释 HQ 进攻窗口、守家路线、据点收益和行动顺序之间的取舍。

## 补给与六项裁决分账本
按本文件第四节逐项列数量、权重、来源和总分。

## 失误与改进
第一名也至少写2条可量化的低效或风险决策；非第一名必须写“实际做法 vs 正确做法、触发条件、预期收益”。

## 与历史对局对比
引用具体 `gameId` 或文件名，比较人数/地图/出生位、HQ伤害、据点、淘汰轮次、总分和本局新发现。

## 总结
### 做得好的
1. {事件证据}
### 下次改进
1. {触发条件与替代动作}
> **核心口诀：{一句可执行原则}**
**一句话总结：{加粗的一句话}**
```

平局必须额外回答：哪些玩家并列最高、六项分数及权重；最后1–2轮哪一个合法动作能破局；平局是主动保分还是误判造成的机会损失。

## 六、标准模式质量检查

- [ ] 文件位于 `records/V3/`，命名符合 `win/lose/rankNN/draw` 规则；agent/模型名是写作者自己的。
- [ ] 元数据、席位表、排名、结束原因、整轮数和 HQ 状态完整且与 `game_over` 一致。
- [ ] 每个关键结论有轮次、席位回合、补给、行动点、坐标和事件依据。
- [ ] 分别统计每个对手，没有把多人局写成单一“敌方”。
- [ ] 有收入、花费、HQ伤害/承伤、据点、军力、补给和 `actionScore` 账本，权重来自本局配置。
- [ ] 淘汰写成 HQ 被摧毁；房主 `turn_skipped`/`host_eliminated` 单独标注。
- [ ] 引用历史对局；有一句话总结；第一名有至少2条失误，非第一名有正确做法和触发条件。
