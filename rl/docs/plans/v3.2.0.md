# v3.2.0 训练方案 —— 把规则算法纳入训练分布

> 状态：**已结项（2026-09-19）**——A1–A6 全部落地；七轮配方实验（A4 / champ / champ2 / champ3 / champ4 / champ5 / r3x）全部跑完并判定。**最终结论：v3.2.0 与 v3.1.1 打平、未超越**（详见 §5.16）。训练与评估均已停止，无后台任务在跑。
> 目标模型版本：**v3.2.0**（模型版本序列，非游戏版本 3.5.3）
> 依据诊断：`arena/matches.jsonl` 11424 局算法对模型对局 + `arena/details/` 逐局明细
> 相关档案：`rl/docs/MODELS_NOTES.md`、`rl/docs/RELEASE_NOTES.md`

## 0. 一句话

v3.x 系列的所有失败模式共享同一个根因——**训练分布之外的策略就打不过**（danger-close 28%、forge 0:48、座位锁，以及本次的算法碾压）。v3.2.0 不再逐个打补丁，而是把「规则算法」这一类**策略形态**直接放进训练对手池，让泛化能力成为训练目标本身。

> **最终结果（2026-09-19）**：这套思路未能兑现。七轮后续实验把奖励、靶子构成、学习率、训练规模、
> 以及「还原 3.x 原配方」逐条证伪——最好产物 champ 在两套 192 局头对头下为 49.2%，而零假设恒为
> 50.0%。完整结论、机制归因与下一步建议见 **§5.16**。

## 1. 诊断：v3.2.0 要解决的问题

### 1.1 核心数据

| 指标 | 数值 | 说明 |
|---|---|---|
| 算法对模型总胜率 | **83.5%** | 11424 局，已剔除随机算法 |
| 模型自我对战胜率（v3.1.1） | **71.0%** | 2688 局，在模型圈子里是强者 |
| 模型对算法胜率 | **16.5%** | 同一批对局反过来看 |
| 各算法对模型 | threat 87.8% / greedy 85.6% / field 83.9% / mcts 76.6% | 对全部 17 个历史模型 |

**结论：这不是能力不足，是分布外泛化失败。** 模型在自己的生态里碾压同类，出圈即崩。

### 1.2 时间线错位（硬证据）

- 算法首次进入竞技场：**2026-09-16 10:54**
- 最后一代模型 v3.1.1 训练结束：**2026-09-11**

模型训练时，threat / field / greedy **在训练对手池里根本不存在**。训练对手池是「锚点模型（`RL_ANCHOR_PROB`）+ PFSP 自对弈快照」，全部是模型。这批对局是拿冻结模型去打全新对手。

### 1.3 三个可修复的行为缺陷

**（a）兵种坍缩**——模型 85% 只出步兵：

| | 侦察兵 | 步兵 | 支援 | 远程 | 重甲 |
|---|---|---|---|---|---|
| 算法 | **44%** | 36% | **11%** | 6% | 2% |
| 模型 | 8% | **85%** | **0%** | 6% | 0% |

侦察兵机动 5 / 成本 38，步兵机动 3 / 成本 45（`src/config/randomMap.ts:272-273`）。算法用便宜高速单位铺开抢点 → 控点收入 265 vs 192（**+38%**）→ 总收入 379 vs 303 → 部署投入 429 vs 362。模型连一个支援单位（治疗）都不出。

**（b）不打总部**——算法赢的 9537 局里：

| 指标 | 算法 | 模型 |
|---|---|---|
| HQ 伤害 | **134.5** | 6.7 |
| 击杀数 | 1.9 | **3.3** |
| 造成伤害 | 436 | **453** |
| 战损 | 3.3 | **1.9** |

模型战术交换全面占优，HQ 伤害只有算法的 1/20。反过来看模型赢的 1887 局，恰恰是 HQ 伤害 85.7、控点收入 247 的时候——**致胜公式就是「抢点 + 推 HQ」，模型会做，只是不稳定**。

**（c）座位无关**：算法先手 86.0% / 后手 81.0%。不是座位锁问题，是策略问题。

### 1.4 趋势（说明修得动）

模型对真算法胜率：v2.6.0 **3.7%** → v3.0.3 **28.9%** → v3.0.4 **35.4%** → v3.1.0 32.7% → v3.1.1 31.4%。

自我博弈确实在缓慢逼出泛化，只是速度远慢于对手迭代。**给对的对手比给更多步数有效。**

## 2. 三条设计决策

### 决策一：不改观测与动作空间（保持 6715 维 / `Discrete(155)`）

HQ 信息**观测里已经有了**：`env.py:1063-1064` 编码双方 HQ 血量，攻击候选里有 `is HQ` 标记位（`env.py:1174`），裁决权重 `enemyHqDamage` / `ownHqHp` 也在规则段里（`env.py:1120-1123`）。模型**看得见却不重视**——所以杠杆在奖励，不在观测。

**收益**：可直接从 v3.1.1（**实际步数 8.8M**，见 §4 的说明）续训，不必从零重训，省下 8.8M 帧。
**代价**：放弃了「显式给模型一个 HQ 距离特征」这条更激进的路径，留给 v3.2.0.1 备选。

### 决策二：算法对手走已存在的 `decide` 通道，不新增桥

`rl/training/local-worker.ts:110` 已有 `decide` 命令：

```ts
if (command.cmd === 'decide') return decideAlgorithmAction(command);
```

返回 `{action: {type, payload}}` 或 `{endTurn: true}`。当前只有 `evaluate_cross.py:342` 在用。而 `LocalHexGameEnv`（`rl/training/local_env.py:44-55`）本来就是同一条 worker 管线。

关键便利：**算法返回的是引擎原生 payload，训练侧直接 `_apply` 即可，不需要映射到 155 动作表**。与评估侧完全同构。

### 决策三：课程式引入，而非直接 40% 起步

模型对算法只有 16.5% 胜率。一上来就把 40% 的对局交给算法，早期样本大面积失败会伤价值函数。采用**两阶段**（复用项目已有的逐代续训习惯，零新代码）：

- 阶段 A：`RL_ALGO_OPPONENT_PROB=0.20`，偏向最弱算法 greedy
- 阶段 B：`RL_ALGO_OPPONENT_PROB=0.40`，转向最强的 threat / field

> **实现修正（P0）**：该概率按「**对局占比**」实现——算法分支在 `_choose_opponent_style` 中优先级最高，不再被 0.70 的自对弈概率稀释。若按最初设想的"插在 self_play 之后"，0.20 会实际变成 0.20×(1−0.70)=**6%**，课程 0.20→0.40 会变成 6%→12%，与"给算法对手足够暴露"的目标不符。修正后的对局构成：

| 阶段 | 算法 | 自对弈快照/锚点 | 规则对手 |
|---|---|---|---|
| A | 20% | 56% | 24% |
| B | 40% | 42% | 18% |

（可选的更优雅做法是像 `RL_LEARNING_RATE` → `RL_LR_END` 那样做进度插值，但要动 `SubprocVecEnv` 的属性同步，本次不做。）

### 被否决的备选

| 备选 | 否决理由 |
|---|---|
| 动作掩码强制兵种多样性 | 硬约束会破坏收敛，且掩盖根因 |
| 直接用熵奖励逼多样性 | 会在终局回填、信用分配差，还可能奖励乱出单位（见 A5 的替代设计） |
| 把 threat 算法重写进 Python | 双份实现必然漂移，违背 `skill/` 单一规范源的项目原则 |
| 从零重训 v3.2.0 | 白扔 10.94M 帧，且观测/动作未变，没有理由 |

### A1 · 算法对手接入（核心）✅ P0 已完成

**`rl/envs/env.py`** — `HexGameEnv.__init__` 新增参数（`env.py:164`）及类属性 `SUPPORTS_ALGORITHM_OPPONENT = False`（`env.py:162`）：

```python

`_choose_opponent_style`（`env.py:544-576`）的分支**放在最前面**（修正见 §2 决策三）：

```python
self.active_algorithm = ""
if (self.algorithm_opponent_pool
        and self.algorithm_opponent_probability > 0
        and float(self.np_random.random()) < self.algorithm_opponent_probability):
    names = list(self.algorithm_opponent_pool)
    weights = np.asarray(list(self.algorithm_opponent_pool.values()), dtype=np.float64)
    self.active_algorithm = str(self.np_random.choice(names, p=weights / weights.sum()))
    return "algorithm"
```

**命名必须分开**（配置侧的池 vs 本局抽中的那一个，类比 `self._self_play_path`）：

```python

# 本局侧：每次 _choose_opponent_style 重抽

```

**不要**把本局抽中的算法写回 `self.algorithm_opponent`（那是构造参数名），否则第一局之后配置就被覆盖了。

`_play_opponent_until_agent_turn`（`env.py:835-894`，分支在 `:855`）的 if/elif 链新增分支：

**`rl/training/local_env.py`** — 新增一个显式命名的方法，**不要**复用 `_rpc` 的返回值语义：

```python
def decide(self, owner: str, algorithm: str) -> dict[str, Any]:
    """走 worker 的 decide 通道。注意：返回值是【决策结果】
    （{action:...} 或 {endTurn:true}），不是游戏快照——worker 响应里的
    state 字段承载的是 handleCommand 的返回值，decide 不改变游戏状态。"""
    return self._rpc({"cmd": "decide", "owner": owner, "algorithm": algorithm})
```

> **坑（已写进代码注释）**：`_rpc` 的实现是 `return response["state"]`（`local_env.py:68`）。对 `apply` / `reset` 而言它是快照，对 `decide` 而言它是决策对象。误当快照赋值给 `self.state` 会直接把游戏状态改坏。

`_algorithm_pick`（`env.py:927-950`）与钩子 `_algorithm_decide`（`env.py:918-925`，基类抛 `NotImplementedError`，`local_env.py:87-88` 覆写为 worker 调用）：

```python
def _algorithm_pick(self, valid):
    if self.algorithm_epsilon > 0 and float(self.np_random.random()) < self.algorithm_epsilon:
        action_type, payload = valid[int(self.np_random.integers(len(valid)))][1]
        self.algorithm_actions += 1
        return action_type, payload
    decision = self._algorithm_decide()          # 子类实现（worker）
    if decision.get("endTurn"):
        return "end_turn", {}
    action = decision.get("action") or {}
    action_type = action.get("type")
    if not isinstance(action_type, str) or not action_type:
        raise RuntimeError(f"algorithm decide 返回缺少 type 的动作: {action!r}")
    payload = action.get("payload") if isinstance(action.get("payload"), dict) else {}
    self.algorithm_actions += 1
    return action_type, payload
```

算法在「无事可做」时返回 `null` → `{endTurn:true}`，与现有循环兼容。**算法无跨调用状态**（每次 `decide` 从快照重建上下文，见 `algorithms/builtin/threat.mjs:344` `decide`），因此 Python 侧逐动作调用的用法是正确的——与 `evaluate_cross` 完全一致。

> 算法不读事件日志（已核实 `algorithms/` 下无 `.events` 引用），因此训练环境的 `eventTail: 0` 裁剪不影响算法决策。

新增两个**诊断计数器**（每局在 reset 里清零，随 `unit_slots` / `action_counts` 同处：`env.py:353-355` 与 `local_env.py:120-123`）：
- `algorithm_actions`：算法座位实际产出的动作数。配了池却长期为 0 = 通道静默失效
- `opponent_rejections`：对手动作被引擎拒绝、降级为 end_turn 的次数（`env.py:885` 的 except 分支）。算法返回引擎原生 payload，该值持续 >0 说明算法视角与引擎校验不一致

**`rl/training/train.py`** — 新增环境变量（`train.py:646-654`，紧跟 `RL_OPPONENT_STOCHASTIC_PROB` 之后）：

```python

### A2 · 算法对手配比

```bat
set "RL_ALGO_OPPONENT_PROB=0.40"
set "RL_ALGO_MIX=threat:0.40,field:0.30,greedy:0.30"
```

**mcts 不进池**：它对最新模型只有 48-59% 胜率，威胁等级最低，采样预算应给 threat / field。
**保留 `RL_ALGO_EPSILON=0.10`**（见 A3）。
**可选 PFSP**：按对每个算法的胜率倒数加权（复用 `_self_play_weights` 的 `(1 - win_rate)^2` 模式，扩展成 per-algorithm 记录）。建议阶段 B 再开，阶段 A 用静态权重。

### A3 · 确定性扰动（必须做）

算法是**确定性策略**：同一状态永远同一动作。模型会过拟合固定走法。以 `RL_ALGO_EPSILON=0.10` 的概率用随机合法动作替换算法决策，成本极低，收益是打断确定性剥削链。

> 注意 `RL_OPPONENT_STOCHASTIC_PROB` 只对**模型**对手生效（`env.py:511-514`），对算法无效，不能指望它。

### A4 · 奖励：补 HQ 项

现状：`_strategic_snapshot`（`env.py:407-426`）只返回 5 个字段（`control_points` / `own_units` / `enemy_hp` / `own_hp` / `nearest_cp`），**HQ 血量被并入 `enemy_hp` / `own_hp`，没有独立项**。`_shaped_reward`（`env.py:428-444`）的项只有占点、敌我 HP、靠近未占点、结束回合惩罚。

新增四个字段与两个奖励项：

```python
# _strategic_snapshot 追加
"enemy_hq_hp": ...,        # 敌 HQ 当前血量（已毁则 0）
"own_hq_hp": ...,          # 己 HQ 当前血量（**不参与奖励**，见下）
"hq_pressure": ...,        # 己方最靠近敌 HQ 的单位的六角距离
"hq_pressure_valid": ...,  # 1.0/0.0：无关卡时（己方无单位 / 敌 HQ 已毁）势能无效
```

```python
# _shaped_reward 追加（签名需扩为 (before, after, action_type, unit_type)）
reward += (before["enemy_hq_hp"] - after["enemy_hq_hp"]) / 100.0 * self.reward_hq_damage   # 默认 0.15
if (before["hq_pressure_valid"] and after["hq_pressure_valid"]
        and before["own_units"] == after["own_units"]):
    reward += (before["hq_pressure"] - after["hq_pressure"]) * self.reward_hq_push         # 默认 0.02
```

**为什么这两项是安全的**：HQ 伤害在游戏裁决里本来就是最大的胜利资源（裁定权重 `enemyHqDamage` 见 `env.py:1120`，threat 算法自己也专门给了 `HQ_DAMAGE_BONUS` / `HQ_KILL_UTILITY`，见 `threat.mjs:140-143`）。这不是发明新目标，而是**把已有终局信号提前显式化**，改善信用分配。

**推进项的两个守卫都是必需的**：
- `hq_pressure_valid`：没有它，己方单位全灭会让距离从 3 跳到 0，白拿推进奖励 → 打开「送死→重新部署」的刷分路径（`test_hq_push_does_not_reward_wiping_out_own_units`）。
- `own_units` 相等：没有它，「最近的那个单位阵亡」会被读成"撤退"而扣分、「新单位出现在己方 HQ」也会进差分。加上这条之后，该项是对**固定单位集**的严格势能差分，满足 potential-based shaping 的策略不变性（`test_hq_push_requires_stable_roster`）。

**`own_hq_hp` 刻意只做读数、不做奖励**：自家 HQ 掉血已被 `own_hp` 项（−Δ/160）与裁决分差（`ownHqHp` 权重）覆盖两次，再加负向项会让"缩家防守"更有吸引力——这是对已学策略的方向性改动，须单独的训练验证（见 R2）。该字段由评估读数 `own_hq_hp_mean` 消费，用来观察"加了打 HQ 的奖励后自己 HQ 有没有被打得更狠"。

新增环境变量：`RL_REWARD_HQ_DAMAGE=0.15`、`RL_REWARD_HQ_PUSH=0.02`。**从保守值起步**（对比现有 shaping scale 0.5 与占点项权重 0.7）。默认值集中在 `env.py` 的 `DEFAULT_REWARD_*` 常量，`train.py` 启动打印引用同一份常量，避免两处数字漂移。

> **量级提醒**：默认权重下"打掉 180 HP 的敌 HQ"整局只值 `1.8 × 0.15 = 0.27`（×0.5 后 0.135），约为胜负奖励（5.0）的 2.7%。这是一个**方向性微调**而非行为反转。
>
> 判断它是否起作用的正确读数是**算法对手场景**的 `eval/random_algo_*_hq_damage`（阶段 B 开 `RL_EVAL_ALGO=1` 后才有），可对标 arena 的 19.7。**不要**看 `random_rule` / `*_champion` 的 `hq_damage`——那两项在 v3.1.1 基线上就已经是 175–180（HQ 满血 180，赢了即打爆），不具判别力，原因见 §6 的口径更正。若算法场景的该读数仍停在 20 附近，再把 `RL_REWARD_HQ_DAMAGE` 提到 0.5 量级重跑一轮，而不是继续调其它变量。

### A5 · 兵种多样性：用「首次部署 novelty」替代熵奖励 ✅ P1 已完成

```python
# _shaped_reward 内，deploy 分支
if action_type == "deploy" and unit_type not in self._deployed_types:
    reward += self.reward_new_unit_type    # RL_REWARD_NEW_UNIT_TYPE，默认 0.05
    self._deployed_types.add(unit_type)
```

`safe` 起见带 `if unit_type` 前置判断：payload 缺 `unitType` 的异常路径不能把空串记进集合，否则那个"兵种"的额度会被白白消耗掉。

选它而不选熵奖励的理由：

1. **即时**——信号在动作当步给出，不依赖终局回填，信用分配容易
2. **有界**——每个兵种只给一次，一局最多 5 次（上限 0.25），不会被刷分
3. **不改最优方向**——它只是填补早期探索空白，不惩罚「重复出步兵」这个可能本就合理的战术
4. **`_deployed_types` 每局清空**——必须清在**两处**，因为 `LocalHexGameEnv.reset`（`local_env.py:91`）走的是 `super(HexGameEnv, self).reset(seed=seed)`，**跳过**了基类 `HexGameEnv.reset`：
   - `rl/training/local_env.py:120-124`（训练实际路径，与 `self.unit_slots` / `self.action_counts` 同处）
   - `rl/envs/env.py:366-371` 基类 `reset`（HTTP 路径）
   - `tests/rl/test_v320_shaping.py::test_both_reset_paths_clear_per_episode_state` 用 `inspect.getsource` 锁死两处，漏一处就会跨局累积、且不报错。

配套监控：`ActionDiversityCallback`（**`rl/training/train.py:527`**，原稿误写为 `env.py`）已有 `explore/*_new_rate`，追加 `deploy/type_entropy`（部署兵种分布的香农熵，5 兵种均匀 = ln5 ≈ 1.61 nats）与 `deploy/scout_share`（直接对应验收门禁「侦察兵占比 ≥ 20%」，v3.1.1 实测 8%）。

> `_deploy_types` 是**窗口内**计数（随 `_picked` 一起每窗口清零），与 `_picked` 的累计语义不同：兵种坍缩问的是"当前策略还有没有多样性"，累计值会被早期窗口稀释。
> 兵种从动作下标反推：`classify_action` 把 deploy 折成候选序号（丢掉了兵种），兵种 = `(index - DEPLOY_BASE) // DEPLOY_CANDIDATES`。

### A6 · 评估场景与 best 选择键分离 ✅ P1 已完成

**`rl/training/eval_worker.py`** — `build_scenarios` 新增算法场景（参数 `algo_scenarios` / `algo_episodes`）：

```python
for algo in ALGO_EVAL_NAMES:          # ("threat", "greedy", "field")，mcts 不进池
    scenarios[f"random_algo_{algo}"] = {
        "map_id": map_id,
        # 注意：算法对手**不是** opponent_style="algorithm"（见下）
        "opponent_style": opponent_style,       # 永不触发的规则兜底
        "algorithm_opponent": algo,
        "algorithm_opponent_probability": 1.0,  # 算法分支持续命中
        "algorithm_epsilon": 0.0,               # 评估要量算法真身，不做确定性扰动
        "_selection": False,      # 记录但初期不参与 best 选择
        "_episodes": algo_episodes,
    }
```

> **原稿的错误**：写成 `"opponent_style": "algorithm"` 会直接 `ValueError` —— `HexGameEnv.__init__` 把 `opponent_style` 校验为 `{mixed, aggressive, defensive, economy}`。算法对手是由 `algorithm_opponent_probability` 决定的 `_choose_opponent_style` 分支，`opponent_style` 此时只是永不触发的规则兜底。`test_v320_selection.py::test_algorithm_scenario_uses_the_flag_not_a_style_name` 锁死这一点。

场景字典用 `_` 前缀携带元数据，`split_scenario` 负责拆分（元数据绝不能透传给构造函数，否则 `TypeError`）：

```python
env_kwargs, in_selection, episodes = split_scenario(kwargs, default_episodes)
```

`evaluate()` 把标记落到结果里：

```python
entry["map"] = env_kwargs["map_id"]
entry["in_selection"] = in_selection
```

`selection_score` 的 `in_dist` 过滤追加一条：

```python
in_dist = [s for s in scenarios
           if s.get("map", train_map) == train_map
           and s.get("in_selection", True)]
```

**旧结果 JSON 无 `in_selection` 字段 → 默认 `True`**，与 `map` 字段的向后兼容处理同构，现有 `tests/rl/test_v303_selection.py` 五个用例语义不变。

**为什么初期不进选择键**：这正是 v3.0.2 的教训——`min_wilson_lb` 被 OOD 崩塌主导，best 挑中 10 万步断点。算法场景在训练早期必然低胜率，若进选择键会系统性偏向「对模型强但对算法弱」的早期断点。**等阶段 B 后期、对算法胜率稳定过 40% 后再纳入**（改 `_selection: True`，另起一次验证）。

**顺带把验收门禁变成每次评估都能读到的量**：`play_scenario` 追加 `hq_damage_mean`（裁决分里的 `headquartersDamage`）、`own_hq_hp_mean`、`scout_deploy_share`（部署侧）、`scout_board_share`（盘面侧）。没有这四个读数，"HQ 伤害 ≥ 60"和"侦察兵占比 ≥ 20%"就只能等手工离线分析。

> 全部场景都被排除时（例如只开算法场景调参）保持 `in_selection` 过滤后再退化为全场景，**不能返回空哨兵** —— 哨兵会让 `score > best_score` 永远为假、`best_model.zip` 永不保存。

新增环境变量：`RL_EVAL_ALGO=0/1`（默认 0，阶段 B 开启）、`RL_EVAL_ALGO_EPISODES=48`。

### 实现约束（A1-A6 共同遵守）

1. **只改 `rl/envs/env.py` 与 `rl/training/local_env.py`，绝不改 `env_v22/v24/v25/v26/v27/v100/v200.py`**——那些是冻结环境快照，用于复现旧模型的训练时行为（`env.py:545-557` 的 legacy 编码器就依赖它们逐格一致）。改动会静默破坏历史模型对手。

### ⚠ 一处配方与文档不符：学习率调度的锚点（既有行为，非本次改动引入）

启动打印是 `lr=schedule 5e-05->1e-05`，但训练表里实到的 `learning_rate` 起步只有 **1.48e-05**，
随后 1.46e-05 —— 也就是**阶段 A 实际几乎全程跑在衰减终点附近**，而非方案写的「5e-05 起、1e-05 收」。

原因在 `make_lr_schedule`（`rl/training/train.py:88-98`）：它用 SB3 的 `progress_remaining`，而
SB3 在 `learn()` 里按 `1 - num_timesteps / _total_timesteps` 计算该值，`_total_timesteps =
num_timesteps + total_timesteps` 是**累计口径**。所以续训时：

```
progress_remaining = 1 - 8804096 / (8804096 + 1200000) = 0.1199
lr = 1e-05 + (5e-05 - 1e-05) × 0.1199 = 1.4798e-05   ← 与实测 1.48e-05 完全吻合
```

函数 docstring 写的「进度按本次 learn 的总步数计」，在**续训**场景下是不成立的（只对从零训练成立）。
这个行为**历代续训全部存在**：v3.1.1 用的是同一组 `0.00005 / 0.00001`，其起点
`progress = 1 - 8.44/10.94 = 0.229` → 实际起步 1.91e-05。所以 v3.x 的每一次续训也都是低学习率起步，
名义值 5e-05 从未真正生效过。阶段 A 的 1.48e-05 比 v3.1.1 的 1.91e-05 还低，仅因为本次增量占比更小
（12% vs 23%）。

**为什么本次不因此重启**：

1. 这是**既有行为**，不是本次改动引入的回归；阶段 A 的起点模型本身就是在该低学习率区间训练出来的，
   继续用同区间与模型自身历史**连续**，不是突变；
2. 项目对高学习率有明确的历史教训（后期胜率震荡），临时改用未验证的高学习率属于引入新变量；
3. 低学习率的影响是「学得慢」，不是「学错方向」，且 P3 有明确的判据（对算法胜率、侦察兵占比、
   HQ 伤害）能度量它是否真的没学到东西。

**如果阶段 A 结束时三个判据读数都没动**，第一顺位要动的旋钮**不是**奖励权重，而是这个学习率锚点。
两条可选修法（留待 P2b 决策）：

- `RL_LR_MODE=constant` + `RL_LEARNING_RATE=5e-05`：最简单，绕过累计口径；代价是失去衰减保护
- 保留调度、把 `RL_LEARNING_RATE` 按 `lr_end + (lr_start - lr_end) × progress_remaining⁻¹` 反解
  （本次需设成约 3.4e-4 才能让实际起步落在 5e-05）：不改代码但数值反直觉，需在启动器里写清注释

更长远的正确修法是让调度按「本次 learn 的增量步数」计算进度（改 `make_lr_schedule` 的进度来源），
但那会改变所有历史配方的实际行为，应当作为独立改动单独验证与记录。

对 v3.1.1 / 阶段 A 交付物 / 阶段 A 末断点三者在同种子下补测对算法胜率
（`temp/v320_*_algo.{json,txt}`）。若对算法胜率**没有**显著提升，那么 A1–A3 这一整条主线
在 1.2M 帧的预算下就是无效的，应当先修 A4 的量纲 + 学习率 + 选择键，再重新设计阶段 B，
而不是按原计划把算法占比提到 40% 继续烧帧。

### 补测结果（同种子 `--seed-prefix 27000`，`--algo-scenarios --algo-episodes 48`）—— 结论反转

| 场景 | v3.1.1（起点 8.8M） | 阶段 A 交付物（8.9M） | 阶段 A 末（10.0M） |
|---|---|---|---|
| `random_algo_threat` | 44%（lb 31%） | 46%（lb 33%） | **17%（lb 9%）** |
| `random_algo_greedy` | 33%（lb 22%） | **46%（lb 33%）** | 25%（lb 15%） |
| `random_algo_field` | 62%（lb 48%） | 67%（lb 53%） | 40%（lb 27%） |
| **三算法均值** | **46.3%** | **53.0%（+6.7pt）** | **27.3%（−19.0pt）** |
| `random_rule`（对照） | 77% | 77% | 54% |
| `random_champion`（对照） | 69% | 58% | 31% |

**结论完全反转，而且指向一个比「配方设计错」更严重的问题**：

1. **A1–A3 是有效的 —— 但只在最开始 9.6 万帧有效。** 交付物（8.9M）对算法均值
   **46.3% → 53.0%**，其中 `greedy` 33%→46%（Wilson 下界 22%→33%，区间不重叠）、
   `threat` 44%→46%、`field` 62%→67%。这是 v3.2.0 全项目拿到的**第一条真实目标上的正向读数**，
   也是**第一次证明「把算法加进训练对手池」这条路走得通**。
2. **随后约 110 万帧把成果全部摧毁且更糟。** 末断点对算法均值掉到 **27.3%**，
   比起点还低 19pt；`threat` 从 44% 崩到 17%。同时 `random_rule` 77%→54%。
   **即：崩溃不是「只在对算法上」的，是整体性的、训练动力学的崩溃。**
3. 因此本阶段的真实结论不是「A1–A3 无效」，而是
   **「配方在约 10 万帧后进入了破坏性训练区间」** —— 96k 帧的收益被后 1.1M 帧的破坏淹没，
   而 best 选择键恰好在崩溃前一刻取到了那个好断点（纯属巧合，不是选择键工作正常）。

**崩溃的候选机制（按可疑度，均需消融验证）**：

| 候选 | 支持证据 | 反证 / 存疑 |
|---|---|---|
| `ent_coef` 0.03→0.05（+67%） | 探索指标在 ~42 万帧冲到峰值（scout 0.283 / 熵 1.09）后**单调回落**，与 9.1M 起的评估下滑**时间吻合**；熵项持续把策略推离已收敛的好解，而 LR 只有 1.0e-05–1.5e-05，**推得动、收不回** | 熵项理应只降不崩，崩溃幅度超出「熵税」的常见量级 |
| 自对弈池填满后的共演化循环 | 快照池在阶段初期为空（退回规则对手），中后期被**当前漂移中的策略**填满 → 对固定老 champion（v3.0.3）的策略可能周期性失效 | 规则对手是固定的，`random_rule` 77%→54% 无法用它解释 |
| 低学习率 + 长程漂移 | §5 已确认实际 LR 1.48e-05→1.00e-05，为历代最低区间 | 低 LR 通常「学得慢」，不常主动破坏 |
| A4 奖励项 | —— | **已排除**：量级 0.135 vs win 5.0，不可能造成退化 |
| 算法对手提供有害梯度 | 20% 对局里被 threat/greedy 打败，可能学到错误的应对 | 前 96k 帧同样有 20%，却是改善的 |

**A4 的另一个副作用**：因为它量级差两个数量级，`hq_push`/`novelty` 这些项**既不能推动策略、
又改变了奖励尺度**（`ep_rew_mean` 不可跨版本比较），属于纯粹的噪声注入 —— 建议要么把量纲改对
（`hq_damage` 需约 0.15→**2.0 量级**才能与 win=5.0 可比，或改成 `/180` 归一化到 [0,1] 再乘权重），
要么在验证前先关掉。

**另一个判据口径问题**：本次补测里 v3.1.1 在三算法场景的 `hq_damage` 均值已是 **94.2**

说明「算法场景」这个口径的 `hq_damage` 也没有判别力（算法对局时长更长、模型能摸到 HQ 的局不少）。
§6 该条判据需要第三次修订：改用**败局中的 HQ 伤害**或**单位时间内 HQ 伤害**这类不饱和量。

```python

```

`--episodes N` 取的是**前 N/2 个种子**这一特定子集，N 越小偏差越大。48 局 = 种子
27000–27023，300 局 = 27000–27149 —— **48 局是 300 局的严格子集**。反推剩余 252 局可得真实水平
（v3.1.1 场景：threat 47.6% / greedy 54.4% / field 65.5%）：**前 24 个种子在 `greedy` 上系统偏难
（33% vs 54.4%，差 21pt）**。

**这条同时废掉其它所有基于 48 局的读数**，包括「阶段 A 末断点对算法 27.3%」与
「48 局 v3.1.1 基线 46.3%」。**判据、止损线、阶段划分里凡是引用这些数字的地方都不可再用。**

**修法（已实施）**：`eval_worker` 新增 `--seed-stride`（默认 1 = 历史行为，不改历史可比性）；
`train.py` 透传 `RL_EVAL_SEED_STRIDE`。`RL_EVAL_ALGO_EPISODES` 建议 **≥192**。

#### 闭环验证（11:26 完成）：**`--seed-stride` 不是修法，只是把误差搬了个位置**

（种子 27000/27006/…/27138，跨 138 个种子）与三种口径对照：

#### 种子区间对照（11:34 完成）：**绝对水平是种子集合的函数，但配对差值仍然有效**

同一份 v3.1.1，只换种子区间（`--seed-prefix 90000` vs `27000`），各 300 局/算法场景：

| 场景 | prefix 27000 | prefix 90000 | 差 |
|---|---|---|---|
| threat | 47% | 36%（lb 31%） | **−11pt** |
| greedy | 51% | 43%（lb 38%） | −8pt |
| field | 65% | 61%（lb 55%） | −4pt |
| **三算法均值** | **54.3%** | **46.7%** | **−7.6pt** |
| default_champion（96 局） | 100% | 100%（lb 96%） | 0 |

**判读（结论比看上去窄，但很重要）**：

- −7.6pt 若按「三场景独立」算 SE=2.4pt（3.2σ），但**三个算法场景共用同一批种子，是强相关的**
  （每个区间整体偏难/偏易：27000 给 47/51/65，90000 给 36/43/61）→ 有效 SE 更接近单场景的
  2.9pt，差值 SE ≈ 4.1pt ⇒ **1.9σ，p≈0.06，处于「不能确立、也不能排除」的灰区**。
- 但方向与量级足够大，**不足以支持「换区间无影响」这个假设**。取保守解读：
  **本协议的绝对水平带一个约 ±8pt 的"种子集合偏移"**，300 局不足以消掉它。

⇒ **可操作结论（比"再多跑几局"更关键）**：

1. **跨模型比较必须冻结同一个种子集合。** 本方案此前所有比较**都用了 `--seed-prefix 27000`**，
   因此 **−20pt 的崩溃、0.0pt 的 A1–A3 效应、0.0pt 的 `ent_coef` 效应全部仍然成立** ——
   它们是同一套卷子上的**配对差值**，而种子集合偏移在配对差值里被消掉了。
2. **报告时区分「差值」与「绝对水平」**：差值是机构内可比的（本方案一切判据都用差值）；
   绝对水平（54.3% 这类）**只在 `27000–27149` 这套种子上成立**，换区间不可直接引用。
3. **不要在一条比较链中途换 prefix**。这等于换卷子，正是 48→300 那次误判的同类错误。
4. 300 局仍是本协议下**能接受的功效下限**（可分辨 ~10pt 级效应）；更小的效应需要更多局数，
   而**不是**靠换区间或调 stride。

**顺带补上的 96 局口径 rule/champion 基线**（与 10.0M 末断点头对头）：
`random_rule` 81%（lb 72%）、`random_champion` **50%（lb 40%）**、`default_champion` 100%。
⇒ 10.0M 的 64% / 31% / 0% 相对这条基线**三个场景全部显著更低**，退化不依赖种子区间。

本次测得 **v3.1.1 对 `threat` 47%（即 threat 赢 53%）**，而竞技场诊断里是

#### 修正后的方向（替代「提高算法占比」）

两条独立证据指向同一结论：**瓶颈不在对手池，在奖励**。

1. **算法对手不是短板。** v3.1.1 从未在训练中见过算法，对算法却有 54.3%（300 局）。
   把算法加进池子（A1–A3）+200k 帧后没有任何可测变化 → 「模型没见过算法」这个诊断假设
   **在 eval 口径下不成立**（需先用 arena 口径复核）。
2. **A4 从未工作。** 诊断里最硬的缺陷是「赢战斗输战争」：算法胜局中模型击杀/伤害/战损全面占优，
   但 **HQ 伤害只有 6.7，对面 134.5**。而 A4 的 `hq_damage` 项打爆整座 HQ 只给 0.135 vs `win=5.0`
   —— **量纲差两个数量级，它在设计上就不可能改变策略**。A5 的 novelty（0.05/兵种，一局封顶
   ~0.125）同样是 10⁻¹ 以下。

→ **下一轮消融的第一顺位变量改为「训练过程的净进展」，而不是任何单项奖励权重。**
A4/A5 量纲修正确实该做（它们从未工作），但**在一条本身不产生净进展的训练过程上做奖励工程是无效的**
—— 先得让过程有趋势，奖励权重才有可测的杠杆。评估一律 `--algo-episodes ≥192`
（**不要**用 `--seed-stride` 当功效修法，见上）。

**优先怀疑（按可测性）**：

1. **学习率过低导致过程退化成了随机游走。** 实测 `lr` 只有 1.0–1.5e-05
   （`make_lr_schedule` 的累计口径把名义 5e-05 压掉了，见 §5），而 `ent_coef` 0.03 持续施加漂移压力
   ⇒ 优化压力 ≈ 噪声，1.2M 帧无趋势。**首选干预：`RL_LR_MODE=constant`（锚定 5e-05）。**
2. **对手随机性 `opponent_stochastic=30%` + 自对弈池共演化**：训练信号的信噪比问题。
3. **`target_kl=0.02` 的早停**：在低 LR 下每次更新本来就小，早停进一步削弱推进。

#### ★★★ 13:00 更正：跨代「净进展」对照被 **anchor 混淆** —— 撤回上一节的跨代结论

**先修正这条指标是什么。** `min_wilson_lb` 并不是一个独立的复合指标，它**几乎就是
`random_champion` 场景（即「打 anchor」）的 Wilson 下界**：

- 评估只有 **3 个场景**（`random_rule` / `random_champion` / `default_champion`），不是 6 个。
- `default_champion` 的 map 是 `default` ≠ `train_map=random` ⇒ 在 `selection_score` 里
  **按 OOD 被排除**（`eval_worker.py:250-253`）。于是 min 只在 `{random_rule, random_champion}` 上取。
- `random_rule` 恒高（v3.0.4 mean_lb 71%、v3.1.1 67%、当前 h2h 80%+）⇒ **min 恒等于 champion 的 lb**。
- 逐点验算吻合：v3.1.1 首点 champion 54% → lb ≈ 0.54−1.96·√(0.54·0.46/96) = 0.44 = 记录的 `min_wilson_lb` 44；
  末点 51% → lb 41 = 记录的 41。

⇒ **`min_wilson_lb` 的语义是「打 anchor 的胜率」，不是「整体棋力」。**

**然后是致命的：评估 anchor = 训练 anchor**（`train.py:1007` 传的是同一个 `RL_ANCHOR_MODEL`），
而它在 v3.1.0 那一代被换过：

| 训练 | 评估/训练 anchor | 该 anchor 的内部步数 |
|---|---|---|
| v3.0.3 / v3.0.4 | `hex_ppo_v3.0.0_..._3000000.zip` | **50 000**（文件名 3M 是预算，见 MEMORY 表） |
| v3.1.0 / v3.1.1 / v3.2.0 | `hex_ppo_v3.0.3_..._5000000.zip` | **5 000 000** |

⇒ 上一节的跨代表（v3.0.4「42→54 有进展」vs v3.1.1「44→41 无进展」）**是在比较两张不同的考卷**：
打赢一个 **5 万步**的模型有大量上升空间；打赢一个 **500 万步**的模型本来就贴着 50% 封顶
（v3.1.1 打 v3.0.3 的实测就是 50% 附近，见下方头对头）。

**撤回上一节的跨代结论「这套配方没有净进展」。** 仍然成立的只有**同代内**的观察：
v3.1.1 自己 25 个点内 champion 胜率 54%→51%（平），阶段 A 12 个点内 45%→23%（降）。
但这两条都只是「打 v3.0.3 的胜率」，同样不足以支撑「配方退化」的一般结论。

### 5.7.2 ⚠ 记账更正：`RL_ANCHOR_PROB` 不是全局占比

`_choose_opponent_style`（`rl/envs/env.py:617`）里**算法分支优先级最高**，先吃掉
`RL_ALGO_OPPONENT_PROB` = 20%；剩下的 80% 才去抽自对弈 70% ⇒ 自对弈实际 **56%**，
其中锚点 75% ⇒ **全局打 v3.1.1 = 42%**。完整构成：

| 对手 | 全局占比 |
|---|---|
| 锚点 v3.1.1 | 42% |
| 快照自对弈 | 14% |
| 算法 | 20% |
| 规则 | 24% |

所以「70% × 0.75 = 52.5%」这个写法从 champ 那一轮起就是错的（前文 §5.5 同步作废）。
`[explore]` 日志的 `algo_episodes` 也可以交叉验证：每 30k 帧约 +70 局，除以全局 350 局 ≈ 20%。

### 5.7.3 根因：续训的实际学习率是 **1.4e-05 → 1.00e-05**，不是 5e-05 → 1e-05

`train.py:88 make_lr_schedule` 直接把 `progress_remaining` 喂给 sb3，而 sb3 的
`progress_remaining = 1 - num_timesteps / _total_timesteps`，其中 `num_timesteps` 是
**累计**值。续训时 9.8M / 10.8M ⇒ progress 只有 **0.093**：

```
lr = 1e-5 + (5e-5 - 1e-5) × 0.093 = 1.37e-5
```

日志实测（唯一值集合）：

| 日志 | 学习率区间 | 唯一值数 |
|---|---|---|
| `train_v3.2.0_champ.log` | `1.40e-05` … `1.00e-05` | 41 |
| `train_v3.2.0_champ2.log` | `1.37e-05` … `1.00e-05` | 38 |

⇒ **每一轮续训从第一步起就贴着时间表地板**，整轮几乎没有梯度步长。

这一条把此前几个孤立观察串起来了：

- 「250 万帧零净进展」——不是没有可学的，是步长被锁死；
- 「champ2 与 champ 的 1M 帧读数同分布」——同上；
- 反过来，A4（奖励量纲 0.15→3.0）之所以**能动**，是因为它改的是**梯度方向**，
  在极小步长下仍然可见；而「靶子占比」只改梯度**权重**，被地板吞掉。

`train.py:92` 的注释「进度按本次 learn 的总步数计」**与事实不符**（文档 bug，待修；
正确做法是让调度按本轮增量重置，或直接用常数学习率）。

### 5.7.4 第三轮方案（champ3）：唯一改动 = 解锁学习率

`RL_LR_MODE: schedule → constant`、`RL_LEARNING_RATE = 2.5e-05`（`RL_LR_END` 同值）。
起点 = **champ**（内部 9.8M，非 champ2——champ2 在两套题上都低约 1pt），帧数 +1.0M，其余全部保持。

- 为什么不是 5e-05：消融 #2 已实测常数 5e-05 **有害**（起点低 8–10pt 且单调下滑）。
  5e-05 是当前地板（1.4e-05）的 3.6 倍，属过冲；2.5e-05 约为地板 1.8 倍，取中间值。
- 为什么常数模式不吃亏：交付侧本来就要求常数学习率（`sanitize_delivery_zip`
  会把 callable 换成常数），constant 与交付口径一致，不引入新风险。

**判据不变**：`27000` 与 `90000` 两套 192 局同时 ≥ 50.0%，再用第三套没见过的题

### 5.10.1 顺带更正一个判据口径：`default` 静态图是**座位决定型**

离线 192 局实测（`temp/h2h_selfnull.json` / `h2h900_null_192.json`）：
**v3.1.1 打自己在 `default` 图上 = 50.0%，且座位是 先手 100% / 后手 0%** ——
即该图先手必胜、后手必败，总分恰好 50% 是"两座位各赢一半"的算术必然。

于是该场景读数的含义被澄清：

| 读数（先/后） | 含义 |
|---|---|
| 100 / 0（= 50%） | 与零假设等同：先手能赢，后手必输 |
| 0 / 0 | **连先手都赢不下来** —— 真实弱点 |
| 100 / 100（= 100%） | 后手也能翻盘 —— 真实强项（champ2 拿到过） |

所以 champ3/champ4 的 0% 是**真实退化**，不是噪声；但作为**一票否决线**它不成立 ——
champ2 在该图拿满分（100%/100%）却是验收轴最差的一个，**两个仪器反相关**。
§6 的「无图低于 45% 一票否决」需改成"多图联合 + 不单独否决"，或在 P3 前重定义。

### 5.10.2 四轮旋钮的共同结论

四次改动（LR↑、锚点占比↑×2、对手集中）**全部落在 champ 及其下方**，
且**改动幅度与两题均值反相关**（越小越好）。这指向一个简单解释：
**这个配方不是在"没学够"，而是已经到达它的不动点**，任何扰动都把它推离该点。

但这与另一个解释**无法区分**：1M 帧 × 有效 LR 1.4e-05 的**梯度总量**可能根本
不足以走出盆地（champ 相对 A4 只 +1.0pt，而每一轮的读数是 ±1pt 量级的噪声）。
要区分二者，只能直接做**规模**实验，而不是继续拧旋钮。

### 5.11.1 源码层面的一个新增机制认识：奖励裁剪先于 shaping_scale

`env.py:551` 的 `return float(np.clip(reward, -1.0, 1.0))` 发生在 `reward_shaping_scale`
**之前**（`:431`），而 `RL_REWARD_HQ_DAMAGE=3.0` 时单项贡献是 `ΔHP/100 × 3.0`：
**一次 ≥ 34 点的 HQ 伤害就顶满 1.0 裁剪**，把 `control_points×0.7`、`nearest_cp×0.025`
等其余密集项一起裁掉。所以 A4（0.15→3.0）那点正向位移是在**饱和区**拿到的，

**这条也给"再抬奖励量纲"这条路设了上限**：继续抬只会加深饱和，不会新增梯度信息。
若将来要再动奖励，正确方向是**降低到刚好不饱和的量级（约 1.0）**，
让 HQ 项仍显著高于其他项而不吃满裁剪 —— 本轮不做，避免与规模实验混变量。

## 5.12 第五轮收尾：champ5 被宿主守卫腰斩，抢救后判读为**明确退步**

### 5.12.1 事实链与根因

- champ5（4M 帧）跑到 **+2.31M 帧（累计 12.12M）** 时以 **exit=1** 死亡。日志最后一行（第 12942 行）是
  `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn","targets":[…snapshot_11320000_steps.zip]}`；
  **无 traceback**、**未写交付模型**，且那个"本该被裁掉"的 `snapshot_11320000_steps.zip` 仍在盘上
  ⇒ 那次 `unlink` 被**宿主**拦下后进程被终止，不是 Python 异常。
- 根因：`train.py:587-592` 每次存快照后会删掉超出 `RL_SNAPSHOT_KEEP`（默认 20）的旧快照；而快照间隔 =
  `RL_SNAPSHOT_FREQ`（默认 5000 次回调）× `RL_NUM_ENVS`（8）= **每 40k 步一个**。
  1M 帧的跑只产出 25 个快照 ⇒ 删 5 次，永不越线；4M 帧的跑产出约 58 个 ⇒ 删约 38 次 + 其他删除
  ⇒ 单个 turn 内累计 50 次删除 ⇒ 撞上宿主的批量删除确认门禁 ⇒ 后台非交互无法确认 ⇒ 整轮被杀。
  **这是宿主环境的行为，不是 `train.py` 的 bug。**
- 修法（**行为中性**）：`RL_SNAPSHOT_KEEP=200`（≥ 本次快照总数 ⇒ 零删除）。中性依据：`env.py:567`
  `_self_play_snapshots()` 只取**按 mtime 最近的 N 个**当对手（N=8，README 写 16），所以保留 20 还是 200
  对对手分布**没有任何影响**，只是不再产生删除。磁盘代价约 1GB。
  （等效路径还有抬高 `RL_SNAPSHOT_FREQ`，但那会改变快照阶梯粒度，故不取。）
- 抢救：快照本身是完整 sb3 zip（`num_timesteps` 可读、含 `policy`），可直接当 `--model` 评估。

### 5.12.2 判读：退步，而不是"没收益"

| 192 局同题配对（anchor = v3.1.1） | `27000` | `90000` | 两题均值 |
|---|---|---|---|

## 5.13 轨迹测试（决定性）：交付点 9.80M 的 50% 在换一套题后**不复现**

用同一把尺子（192 局配对、anchor = v3.1.1、`--seed-prefix 27000`）测 champ 训练内的验收轴轨迹。
两点说明：A4 的首个快照（8.84M）就是 **v3.1.1 + 40k 帧**；champ 的交付断点是 9.80M。

| 断点 | 累计步数 | 对 v3.1.1 | 先手 / 后手 | rule |
|---|---|---|---|---|
| A4 首个快照 | 8.84M（= v3.1.1 + 40k） | 44.8% | 53.1 / 36.5 | 84.9% |
| champ 起点附近 | 9.24M | 40.1% | 47.9 / 32.3 | 81.8% |
| | 9.60M | 45.8% | 57.3 / 34.4 | 82.3% |
| **交付断点** | **9.80M** | **50.0%** | 58.3 / 41.7 | 87.0% |
| | 10.00M | 44.8% | 54.2 / 35.4 | 83.9% |

- **交付点是五个点里的最大值，比四个邻居高 4.2–9.9pt。** 剔除它，剩下四点的均值只有 **43.9%**
  （五点全算的均值是 45.1%）。
- 五个点的 sd ≈ 3.4pt，与单点 s.e.（n=192 时 ≈3.6pt）同量级 ⇒ 单点读数本身不可作依据；
  champ2 / champ3 / champ4 / champ5 的"两题均值"排序看起来像随机排列，正是这么来的。
- 顺带解释了一个更早的谜团：**v3.1.1 + 40k 帧就掉到 44.8%**（LR 才 1.1e-5、约 8 次更新），
  说明"基线"本身站在一个很窄的峰上，离开它的第一步就是下坡。

**跨第二套题复核（这一步很关键，它限定了"选峰"的量化口径）**：

| 断点 | `27000` | `90000` | 两套均值 |
|---|---|---|---|
| 9.60M | 45.8% | 47.4% | 46.6% |
| **9.80M（交付）** | **50.0%** | 48.4% | **49.2%** |
| 10.00M | 44.8% | **50.0%** | 47.4% |

- 交付点在两套均值上只比两个邻居高 **1.8 / 2.6pt**，而不是单题口径的 4–5pt。
- **而且"最大值落在哪个断点"两套题给出的答案不一样**：`27000` 认为是 9.80M，`90000` 认为是 10.00M。
  在两套题上同时测的三个断点里，**没有一个能在两套上都不低于 50.0%**
  （9.80M = 50.0/48.4，10.00M = 44.8/50.0）。
- ⇒ 结论要写得更准：**单题口径下的 ±4pt 差异主要是"策略 × 题目集"的交互噪声，不是棋力；
  本仪器在 n=192 时无法分辨 checkpoint 之间的好坏。** "交付 49.2%" 相对邻居的 +2pt 优势
  与 best-of-run 选择的回归均值效应同量级，属正常乐观偏差。
- ⇒ **"schedule + 长程"的启动前提不成立**（轨迹无上升趋势，且峰值在换题后不复现）。
  `run_train_v320_champ6.bat` **不启动**（保留为档案），`run_train_v320_champ5r.bat` 已标注作废。

3. **归属说明**：r3x 的 LR 同样被累计口径锁在 1.42e-05 → 1e-05，"没涨"里有一部分可归因于此；

## 5.16 结论（定稿 · 2026-09-19）

1. **v3.2.0 没有超越 v3.1.1。** 最好产物 **champ**：两套种子集 192 局头对头 = 50.0% / 48.4%
   （均值 **49.2%**；零假设结构性恒为 **50.0%**）。其相邻断点的两套均值为 46.6% / 47.4%，
   而"哪个断点最好"在换题后翻转（§5.13）⇒ 交付读数的 +2pt 属 best-of-run 的正常乐观偏差，
   **整条血统的上限就是"单套题上摸到 50.0%"，从未在两套题上同时越过 50%。**
2. **七轮改动全部落在 40–50%，无一条产生可复现的正向位移。** 名单（`27000` 题单套读数）：
   A4（奖励）46.4 / champ（靶子+规模）50.0 / champ2（锚点占比）49.0 / champ3（解锁 LR）46.9 /
   champ4（集中靶子）47.9 / champ5（拉长规模）46.9 / **r3x（还原 3.x 原配方）45.0**。
   唯一稳定规律：`schedule` 优于 `constant`（等长对照 49.2/47.9 vs 46.6/46.6，且 `constant` 越长越差）。
3. **仪器分辨率是硬约束**：单题 192 局 s.e. ≈ 3.6pt，而换一套种子的整体位移可达 ±4–7pt
   （算法轴实测：v3.1.1 在 `27000` 为 54.2%、在 `90000` 为 46.7%）。
   **要判 2pt 级差异，本仪器需要每套 2000+ 局、多套**；当前 N 不足以支撑"超越"级结论。
4. **配方路线正式关闭**：五条路径（奖励 / 靶子构成 / 解锁 LR / 拉长规模 / 还原 3.x 原配方）
   全部证伪；§5.15.2 进一步给出「同配方在同一起点上重复应用，收益为零」的直接证据
   ⇒ **不要再开新的配方旋钮轮次**，除非先改观测/动作空间。
5. **下一步只剩结构性改动**：从零训练更大容量（`RL_NET_WIDTH` 仅从零生效，`train.py:826`；
   10M 帧 @ ~110fps ≈ 25 小时，以天计），或改观测/动作设计。**若走这条必须先加
   `RL_SNAPSHOT_KEEP=200`**（§5.12.1），否则长跑会被宿主的批量删除门禁杀掉。
6. **交付口径**：交付 **champ**（`hex_ppo_v3.2.0_20260918_random_selfplay_10000000.zip`，内部 9.8M）并如实标注
   「与 v3.1.1 打平（两题均值 49.2% vs 50.0%），未超越」；不得写「超越 3.x」。
   **r3x 不交付**（人工终止，未产出 `rl/models/hex_ppo_v3.2.0_r3x.zip`）。

### ⚠ 更正：HQ 判据的原口径错误（2026-09-18，训练期实测发现）

`hq_damage_mean` 在评估场景里**会饱和**：`maps/default.json` 的 `headquartersSpec.hp = 180`，
赢了通常就是把 HQ 打爆。实测 **v3.1.1 同口径基线（6 局/场景）** 已经是
`174.7 / 174.7 / 180.0`、胜率 100% —— 也就是说原判据「≥ 60」**基线本身就已满足**，不具备判别力。

那个「当前 19.7」来自 **arena 对算法**口径（`arena/details/`）：模型对算法多半在输，很少摸到敌 HQ。
两个口径不可比 —— 这是本方案 §1 与 §6 之间的一个口径断裂，原稿没发现。

**修正后的判据**（三选一，P3 前敲定）：

- **首选**：用**算法对手场景**的 `hq_damage_mean`（阶段 B 开 `RL_EVAL_ALGO=1` 后 `random_algo_*`
  自然产出），与 19.7 同源可比。目标仍取 ≥ 60。
- 备选：改用**败局中的 HQ 伤害**（衡量"即使打不赢也能咬掉多少"），避免被胜率放大。
- 备选：用不饱和的率量（HQ 伤害 / 局时长，或 HQ 伤害 / 己方部署投入）。

**明确不要做**：拿 `eval_worker` 场景的 `hq_damage` 去比 19.7。

**验收报告必须写明 artifact 的实际 `num_timesteps`**，不能照抄文件名里的帧数——交付的是训练期
best 断点，文件名末尾是计划预算（v3.1.1 文件名 10 940 000 / 实际 8 800 000；v3.1.0 文件名
1 500 000 / 实际 100 000）。这一条同时是历史教训的延续：v3.1.1 的 best 出现在"仅训入 36 万帧"
处，说明在分布漂移期间 best 选择键本身就会偏向早期断点。

| R1 | 算法确定性 → 模型过拟合固定走法 | 高 | `RL_ALGO_EPSILON=0.10` + 每局新随机图 + 可选 PFSP |
